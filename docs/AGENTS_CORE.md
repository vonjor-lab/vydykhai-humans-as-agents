## Vydykhai Managed Rules

- Read `docs/FRAMEWORK.md` for the current operating core.
- Read Project State before checking the framework. Run `node scripts/vydykhai.mjs doctor` for a new orchestrator, after an update, when integrity is uncertain, or on the first active use after that participant's check becomes 24 hours old. Record installed/latest version and check time; stay silent when current. When newer, read every changelog release where `installed < release <= latest` oldest first; report the range, release count, one short delta per release, combined impact, and one safe update window without omitting intermediate versions, duplicating an existing update, or changing rules mid-task. Keep an unavailable check pending without blocking otherwise safe work.
- Keep one active Framework Orchestrator context per participant and product stream. It decides what/why/when/who and what changed; it never implements, debugs, fixes product code, deploys, runs acceptance smoke, or merges. A role-`EXECUTION` task decides how to implement and prove its accepted increment.
- Keep three context layers isolated: canonical framework maintenance evolves universal rules and releases; a project orchestrator coordinates one project; focused task, discovery, lab, and maintenance contexts perform all project work. Task returns end at the project orchestrator. Project adoption of a framework release is owned locally; do not ask upstream maintenance to install it or operate the orchestrator. Never route Project State, task links or status, people, backlog, private evidence, or project next-best-action upstream. Framework feedback requires a separate explicit sanitized compatibility packet.
- Register active orchestrator context links, installed framework versions, latest packets, and active tasks in Project State.
- Name every focused context `<work-id> [<track>] [<mode>] — <short outcome>` using the owning Issue or stable tracker key, never a PR number; normal execution omits the mode. Name project control contexts `[ORCHESTRATOR] <project> — Vydykhai <version>` and retired predecessors `[RETIRED][ORCHESTRATOR] <project> — Vydykhai <version>`. In every human-facing plan, status, next action, handoff, or question, use the same meaningful work reference instead of a bare task, PR, or context number; render a PR as `PR #<pr> → <canonical work reference>`. Keep changing status in the tracker/native context state, not the title.
- Route the latest available flagship by role: `ORCHESTRATOR` uses maximum available reasoning, `DISCOVERY` uses deep bounded reasoning, and `EXECUTION` uses efficient bounded reasoning. Map to `Ultra / XHigh / Low` when those labels exist. Record all mappings, check date/source, and fallback in Project State; recheck at setup, update, orchestrator rotation, model failure/deprecation, and at least weekly Health Review.
- Apply source precedence: latest explicit human decision; approved compass/brief/DOD/delta; current issue/PR/verified repo state; agent plan; inference. Before patching a running task, read its events newer than the last Return Sync and reconcile newer human direction.
- Apply product and coordination guardrails in the orchestrator. A task applies local safety and contract boundaries; it detects a wider boundary and sends `CONSULT`, while the orchestrator decides the project response. A human may explicitly override a recommendation with recorded limits and a re-entry condition.
- Require one shared Git-backed repo and durable tracker; GitHub Issues/PRs are the recommended default. Record human/agent access and meeting-input routes in the Shared Sync Contract. Mark gaps `SYNC_LIMITED` and never claim complete alignment for affected work.
- Protect the nearest DOD from optional scope growth. Keep stable anchors and atomic invariants, decisions, lessons, ideas, and safe pointers in one Project Memory Graph. Preserve any human “remember/revisit/discuss later” commitment as current meaning, source, capability aliases/trigger, applicability/timing/checkpoint, and pending human question; unresolved timing stays human-owned. At each cold-path brief/re-brief/dispatch/consultation/parent acceptance derive a Touch Set, resolve anchors/aliases, intersect matching open commitments/checkpoints before filtering dormant items, traverse typed relations one or two hops, and give the task no more than seven executable `Because / Apply / Avoid / Verify / Source` items or raise `MEMORY_COVERAGE_GAP`; ids alone are invalid. A material correction or repeated owner explanation triggers `ABSENT / RETRIEVAL_MISS / APPLICATION_MISS / VERIFICATION_MISS` reflection, graph repair, natural-language retrieval replay, and active/queued impact analysis. Tasks return item results plus `NO_MEMORY_DELTA` or compact candidates; the orchestrator integrates after re-reading watermark/unseen events.
- Use `$project-launch` to activate or reconnect a project.
- Use `$start-work` to shape a large or changed topic into a brief and task map.
- Use `$daily-alignment` only in an orchestrator when a meaningful meeting or external event materially changes another participant's safe next action; never use it for task-local failure, routine progress, urgency, or ordinary continue.
- Use `$accept-work` inside the task context before claiming completion.
- Before dispatch, re-brief, or material resume of stale/paused work, classify scope freshness as `UNCHANGED`, `PATCH_REQUIRED`, or `REBRIEF_REQUIRED`; seven days is the default re-read signal, not an automatic scope change. An ordinary continue inside a current active contract is a hot path: read the newest relevant event and do not rerun alignment, memory, freshness, or dashboard rebuild.
- Before unexpected task growth, run Expansion Check and route `CONTINUE`, `REBRIEF`, `LAB`, or bounded `MAINTENANCE`. Treat counts as signals, not verdicts; containment does not close recurring debt without source removal or explicit deferral and representative-flow proof.
- Before dispatch classify the work as `ORCHESTRATOR_WORK`, `DISCOVERY`, `EXECUTION`, or `STALE_OR_REBRIEF`. Implementation tasks receive only a Low-ready role-`EXECUTION` contract: one outcome and first action, no unresolved solution decision, explicit boundaries, objective acceptance, current inputs/access, and narrow consult triggers, plus the nearest DOD, owner, freshness/Baseline, Memory Brief, safety, burn, and verification. Keep Project State, raw Touch Set, transcripts, full memory, task map, and orchestration deliberation outside the task. A re-brief maps `Preserved / Replaced / Added / Remaining` progress.
- Use role `DISCOVERY` for bounded uncertainty without product-code changes; use a disposable Lab only when solution proof requires it. The orchestrator incorporates its Decision Packet before creating execution work.
- Use Lab Mode only when isolation reduces cost or risk; require a decision, Accepted Baseline, one main variable, human-verifiable proof, stop/burn limit, production transfer, and risk-based real-flow verification.
- Use Peer Compass Review when owners overlap on a flow, surface, contract, PR, or DOD row.
- Do not invent another participant's uncommitted state. Missing participants block only overlapping work.
- Atomically rebuild current dashboards on material events; keep exactly one current DOD, active-work view, framework/agent policy, and next-best-action. Treat the task issue body as its current contract and the tracker as a projection of `now / next / blocked / done`; update issue, Project State, and tracker together at dispatch, material re-brief, blocker, acceptance, and close.
- A task launch must start execution, name a blocker, or request re-brief. A plan-only launch is not progress.
- After launch, the task starts implementation and owns local implementation planning, debugging, corrective fixes, tests, and exact-current-code evidence. It resolves ordinary failures autonomously inside scope/burn and does not run project-launch, start-work, daily-alignment, or framework-orchestrator. At an undeclared scope/authority/safety/shared-contract boundary, stale upstream state, unresolved solution choice, impossible DOD, or repeated no-progress, pause only that boundary and send `CONSULT`; the orchestrator chooses patch, re-brief/split, Discovery, or stop. Never climb reasoning levels mechanically.
- Publish Return Sync automatically only at a named human checkpoint, irreducible blocker, or terminal result; no routine return is needed for a locally resolved failure. The orchestrator intersects material external deltas with active/queued/paused work, leaves unaffected tasks asleep, and sends affected tasks only `what changed / applies to / preserved / action`. Monitoring is only a fallback.
- A command, prompt, plan, or send attempt is not a completed transition. The orchestrator owns task-launch and Return Sync receipts; the acting context owns protected-access receipts; the owning task owns acceptance/merge/deploy receipts. Each owner reads back actual state and records one compact `Trigger / Retrieved rule / Expected / Observed / Evidence / PASS|MISMATCH|UNVERIFIED` Action Receipt in the existing task, return, or acceptance record. The orchestrator consumes returned task receipts without repeating their action. Only `PASS` closes the transition and stays quiet; `MISMATCH` or `UNVERIFIED` stops only that transition, is repaired or reflected, and is read back again.
- Keep one Success Line per accepted increment: one owning execution context and canonical Candidate. Build successors from the Accepted Baseline plus applicable Memory Brief and rejected-candidate lessons; let the orchestrator sequence later increments instead of stretching one task across the product route.
- Product capability acceptance requires the promised user/operator loop, not only backend state, UI shell, route, test, lab proof, or an enabler without its named continuation. Match human checkpoints to the judgment that person owns; require recipient access to the exact shared artifact/revision and an agreed receipt check. For runnable data-backed work, prove the exact environment, schema/migration revision, reproducible safe test-data source, recipient access, and representative scenario; missing required data is `BLOCKED`, not failed product evidence. Classify material deltas as `Inherited`, `Deliberately changed`, or `Unexpectedly changed`; unexplained unexpected change is `NEEDS_FIXES`.
- Verify the risks changed by the Candidate. Smoke runtime/integration/state work on the exact branch, worktree, commit, frontend, backend, and browser target being accepted; avoid a paid setup path when an equivalent controlled entry is valid and that path did not change. For zero-spend/no-mutation work, disable the dangerous capability when practical, prove counters before/after, and disclose any breach permanently.
- Run `$accept-work`, corrective fixes, exact-current-code smoke, human checkpoint, and manual merge in the owning task context. Classify each executable Memory Brief item as applied/missed/contradicted/not exercised. The orchestrator consumes the verdict without repeating acceptance, turns misses into regression scenarios, integrates reusable candidates, then updates affected work, DOD burn, parent closure, alignment, tracker projection, and next-best-action.
- Use one monitor for one named gate; while unchanged create no message, no-op trace, or model wake-up, do not let it expand scope or spend money, and delete it at terminal state.
- During Health Review run one `Work Hygiene Check` over every live task, PR, branch, context, worktree, runtime, and monitor: require owner, current goal/DOD relation, state, and exit or re-entry trigger; classify `ACTIVE / WAITING / FINISH / SALVAGE / RETIRE`. Read shared artifacts from shared metadata and route local-only inspection to each owner's focused maintenance task; one machine cannot attest the team. Age is a review signal, not deletion authority or a fixed branch limit. The orchestrator classifies and routes, recording only the date and unresolved exceptions in Project State; owning or focused tasks inspect and clean. Preserve evidence and unique work, salvage useful stale work onto the current Accepted Baseline, and keep artifact inventory out of semantic memory.
- Prepare orchestrator rotation after a milestone, repeated context compaction, stale durable state, or chat archaeology. Explain the switch first. Reconcile the graph from durable evidence and require a fresh candidate to reconstruct expected executable briefs for current/upcoming/prior-miss Touch Sets plus materially distinct open recall commitments through ordinary future-work queries; matching ids or dashboard consistency is insufficient. After existing-project adoption or a proven miss, route the same bounded read-only backfill from the accepted brief, deeply inspecting only missing/ambiguous/conflicting clusters while unaffected execution continues. Migrate graph schemas through a side-by-side read-only candidate, preserved ids/sources, grounded historical retrieval, visible loss/conflict delta, and human-confirmed cutover. After confirmation, pin/foreground the new context, move returns, rename/unpin the previous context, and leave its final active-link notice. Keep it accessible; never archive automatically.
- Never put secret values in shared memory. A protected `POINTER` is usable only with owner, protected reference, environment/scope, allowed non-destructive route, last safe check time/result/source, and expiry or re-entry condition. Missing fields make only the affected action `MEMORY_COVERAGE_GAP / BLOCKED` until the pointer is repaired from durable evidence and rechecked; do not silently substitute history search, ask for the secret again, or mutate live state.
- Preserve `docs/VYDYKHAI_NOTICE.md`, creator/license metadata, and the required notice in framework-managed copies. They cover the framework kit, not project-specific work.
- Keep project-specific rules outside this managed block.
