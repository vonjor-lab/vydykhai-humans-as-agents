# Framework Efficiency Transition

Approved direction: 2026-09-29. Owner: framework maintainer. Status: IN_PROGRESS.
This is the durable plan for framework development, not a project instruction or an installed workflow. Read it when continuing this transition, not during ordinary product tasks.

## Outcome And Rationale

Increase retained accepted product outcomes per whole-chain allowance and time as architecture grows. Reduce repeated discovery, repairs of accepted behavior and human reminders. Shorter prompts, more rules, a new model or a version number do not establish that outcome.

The recurring failure is a combination of tangled implementation, unproven module autonomy, repeated context loading and conflicting control instructions. Do not assume modularization is already complete before testing its benefits. Test the transition from one useful legacy capability to a closed module, then its independent reuse. Do not require a whole-platform rewrite before the pilot.

Use one cycle: goal -> applicable decisions -> module boundaries -> sufficient context -> delivery -> proof -> retained result -> next action. Preserve human authority, explicit pauses, accepted releases, open obligations and shared meaning across models, harnesses and people.
