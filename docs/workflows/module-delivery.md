# Module Delivery Cycle

Purpose: accumulate accepted product capability while reducing repeated context, rework and total allowance per accepted outcome. Modularity is a standing acceptance constraint, not a competing product DOD. This is the shared decision contract for shaping, preparation, Discovery, Lab, execution and acceptance; their event workflows own the mechanics. Read it on activation or a material boundary decision, not on every continuation.

## One Outcome, One Cycle

| Step | Existing owner | Required result | When incomplete |
| --- | --- | --- | --- |
| 1. Locate | Orchestrator | Product outcome, applicable prior decisions, accepted baseline, affected module identities and consume/change/create intent. | Missing facts: bounded preparation. Contradictory purpose or boundary: one owner decision. |
| 2. Contract | Orchestrator with the module owner | Public entry/output, applicability, preserved behavior, authority, completion test and one outcome owner. | Unresolved solution: bounded Discovery. No blind implementation. |
| 3. Prepare | Orchestrator assigns/reviews; preparer retrieves | Sufficient current public contracts, obligations and exact owned edit/test locations. | Reuse valid findings; fill the named gap or use the accepted fallback. Never recursively prepare preparation. |
| 4. Deliver | Owning task | Fixed Candidate implements the authorized increment, with tests and required docs/map changes. | Correct ordinary failures within scope/burn. New boundary or exhausted approach: CONSULT with evidence, not another full restart. |
| 5. Prove And Retain | Task proves; orchestrator consumes Return | Required input-to-output behavior, connection proof when packaging, explicit remaining work, integrated shared meaning and next product action. | Keep useful partial evidence without promoting it to parent acceptance. Route the exact gap to one owner. |

A step is a decision, not necessarily a new task, model call or artifact. Reuse the existing brief, Module Contract, map, graph, Candidate, Execution Lease and Return. An already sufficient current packet skips retrieval. Approval of an existing plan authorizes its ordinary continuation, not a new request at each step.

## Distinct Sources Of Truth

| Existing artifact | Question it answers | Owner and update boundary |
| --- | --- | --- |
| Compass / brief / DOD | Why this outcome, and what counts as progress? | Orchestrator maintains approved direction; human owns material goal/authority changes. |
| Memory graph | What decisions, reasons, rejected paths, insights and commitments apply? | Orchestrator integrates source-backed candidates from tasks; preserves unresolved obligations and supersession. |
| Code/module map and index | Where is each responsibility, contract, public dependency and verification route? | Executor updates affected entries in the Candidate; initial project coverage follows activation. An index locates; it does not replace meaning. |
| Module Contract, consumer view | What can be used without opening the module? | Module owner maintains entry/output, applicability, release identity, dependencies, failure semantics and connection evidence. |
| Module Contract, maintainer view | How and why does this implementation work? | Executor updates algorithm, invariants, rejected alternatives and tests with an authorized change. Consumers do not load this view. |
| Project State / task checkpoint | Who acts next, on what, and when does a wait end? | Existing control owner; not another semantic memory or copy of code. |

Link these by stable module/entity identities and authoritative sources. Do not copy whole histories into each packet. Follow applicable meaning and reverse consumer obligations; stop code expansion at accepted public boundaries. A short packet missing an obligation is invalid; a long search transcript is not a useful packet either.

## Locate Before Editing

Declare consume, change or create for every affected capability, including dependencies of a new composite. A composition owns its wiring and outcome, not its children's implementations. A consumer reads only the relevant public contract, release/dependency identity, operational requirements and applicable memory; the same restriction applies to cheap preparation.

A module is a coherent, independently usable capability, not necessarily a process, microservice, file or model. A modular monolith is valid. File length is a review signal: split by responsibility and stable interfaces when that reduces coupling, not by arbitrary line counts. No mandatory migration to services or one module per helper.

The orchestrator must raise a boundary decision itself when there is no proven module for a promised reusable capability, responsibilities are tangled, consumer work requires producer internals, or repeated local fixes leave the promised end-to-end behavior unowned. Before more affected implementation, name the current evidence, external intervention, smallest proposed repair, preserved behavior, acceptance, owner and next action. Do not wait for the user to discover the mismatch.

Before accepting material scope growth, apply [goal and necessity review](module-context.md#goal-and-necessity-before-implementation): bind the increment to the accepted platform goal, affected entity/ownership invariants and combined consumer test. Each new mechanism needs an evidenced gap and comparison with existing public mechanisms. Use the existing fresh REVIEW perspective to challenge necessity before implementation, including required security guarantees. A valid internal design does not prove that the product needed it. An unchanged-boundary correction reuses the accepted decision; the reviewer is not another permanent orchestrator.

Explain the benefit plainly: "This connection still depends on manual repair. I recommend finishing that module's public boundary first, keeping the working parts unchanged, so later connections do not repeat this work." Reuse explicit boundary/development approval; an ordinary internal fix stays with its task. A tactical demonstration request does not silently cancel modularity. Resolve a conflicting request through one explicit choice; the human may change direction. A temporary exception retains truthful limits, owner and return condition, not repeated nagging. Explicit pauses stay paused; independent safe work continues.

## Prepare Or Discover

Use [Context Routing](context-routing.md) for model/cost selection: flagship/Low orchestration with bounded High recovery; flagship/High solution Discovery; lowest proven capable profile for retrieval and Low-ready execution. Respect explicit human model choices. Cheap is not a substitute for capable.

Preparation finds facts and routes under the orchestrator's question; it neither designs the solution nor enlarges scope. Discovery decides unresolved design using those facts. Lab tests one uncertain proposition under representative conditions and a burn cap; it does not silently convert an experimental success into a production module. Maintenance removes a demonstrated recurring cause and returns to product work. No new permanent role is required.

For new prepared implementation packets use [Module-Bound Context Packages](module-context.md). Retain accepted legacy workers until a safe rebrief; do not claim that their old packet enforces module access. An unsupported harness remains an explicit limitation, not an excuse to restart all tasks.

First inspect already authorized sources and edit/test paths locally. An information gap that these sources cannot resolve returns a precise question and preserved progress to the orchestrator. Missing fact -> narrow preparation supplement; missing solution -> Discovery; environment failure -> scoped repair; authority conflict -> decision owner. Retain the existing outcome owner and Candidate. Repeated failure without new evidence changes the approach, not the size of the same search.

## Prove The Promised Boundary

Before changing implementation, derive expected behavior and coverage from the approved public input/output contract, independently of whichever stages currently pass. Preserve the last accepted release. Record what the earlier success actually proved: clean entry, prepared intermediate, manual repair, declared internal model, or unknown. A public invocation by a person is not itself manual repair.

For claimed autonomous multi-stage behavior, the maintainer maps applicable requirements/failures through detection -> operation selection -> recheck/alternative -> termination -> observable output. This belongs inside the module; a project orchestrator is not a per-input runtime controller. Do not mandate a dispatcher where a solver or pipeline already owns the loop. A missing transition is a scoped gap, not permission to reinvent the system.

Acceptance under [Accept Work](accept-work.md) requires the promised successful path as well as failures, retained and independent new cases, clean-start repetitions and one exact Candidate. Rejection gates, helper tests, saved intermediates or operator-rescued outputs cannot establish an unexercised full path. Account for required entities/stages from the authoritative input, including failed/unexamined ones. Distinguish technical failure, incomplete search and proven constraint infeasibility; a timeout does not prove impossibility. Finite evidence never guarantees all inputs.

Packaging additionally requires an independent consumer using the released artifact and public documentation/dependencies, without producer source, private imports, ad hoc tuning or hand-carried intermediate repair. Declared internal AI is permitted if it belongs to the contract and reproducible runtime; hidden assistance is not. Behavior acceptance and packaging readiness stay distinct.

If a connection fails, retain both releases and diagnose public inputs, versions, environment and contract first. Only an evidenced internal defect or approved development opens the relevant maintainer boundary. Then create a new Candidate, prove retained/new behavior and return it to closed consumption. Do not let an integration task quietly become a producer rewrite.

## Retain And Continue

Required documentation is part of the Candidate: changed module rationale, public contract, code/map routes and verification references. A preparer may draft factual updates; the executor verifies them. The orchestrator accepts shared decision/insight/commitment candidates, checks the next retrieval can find them, and retains unresolved obligations. No automatic whole-graph rebuild.

Use [Memory Retention And Storage](memory-storage.md) for each semantic integration. Stable-entity refinement and explicit supersession preserve history; physical capacity cannot silently suppress a write. A pending delta with an owned recovery route is retained evidence, not completed integration or permission for another dependent task to ignore it.

Return delivery is not product acceptance. The owning task sends its exact scoped proof through the existing Return route; the orchestrator consumes it, updates the parent DOD and either dispatches the next authorized action or records a concrete wait. A helper slice cannot close the whole module. A Guard or update message cannot replace the pending outcome, next action or question to the user.

Measure retained accepted outcomes, first independent connection success, repeated regressions, time and whole-chain attributable usage. Include preparation, execution, review, recovery and coordination. Use dated coefficients only as estimates when actual allowance attribution is unavailable; do not announce savings from smaller packets alone.

## Weekly Architecture Review

At first active use after confirmed weekly allowance renewal, run one bounded review in the existing Health Review, not seven days after its last completion. Record quota/window identity, fresh reset source/time, budget, completion evidence and next due in Work hygiene; retain one owned return obligation in Detours And Recall. A previous forecast alone does not prove renewal. If unavailable, agree a review window once; without a weekly quota use an agreed weekly budget/window.

Protect planned delivery capacity even after renewal. Low remaining capacity defers broad review to a concrete safe checkpoint or human budget choice. Urgent safety/contract violations still receive immediate scoped handling. Preserve the window binding through compaction, rotation and tactical postponement; replace the same obligation on the next verified window, not duplicate tickets.

Use maps, public contracts, changed task briefs/Returns and acceptance/access metadata, not closed-module source or a full inventory crawl. Check course, module boundaries, hidden intervention, repeated consumer context, current docs and due exceptions. Reuse accepted unchanged evidence. A clean result stays quiet; an evidenced gap gets one owned proposal with benefit, cost/risk, preserved modules, acceptance and safe checkpoint. Reuse an existing owner.

Already approved work proceeds without another permission. New refactor scope, budget or priority requires the human's choice. Guard remains liveness-only: no extra timer, background model wakeup, replay of missed weeks or messages during unchanged waits. Explicit pauses remain paused. On resume or acceptance, continue the product plan, not maintenance for its own sake.
