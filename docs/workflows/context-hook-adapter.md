# Opt-in Lifecycle Context Adapter

This bounded POSIX adapter supports the command-hook protocol documented in the [host Hooks guide](https://learn.chatgpt.com/docs/hooks). It is inert until separately configured and trusted. Shipping the script does not enable hooks. Keep configuration in a disposable test environment or as a review template until adoption is explicitly accepted; never install global hooks or bypass native trust as part of a framework test.

## Boundary

`scripts/context-hook.mjs` consumes one JSON callback on stdin. Fixed arguments are `--workspace <canonical-root> --command <exact-command> --state <relative-state-file> --metadata <relative-existing-directory>`. They belong to the reviewed hook definition, not prompt/tool text. Register synchronous UserPromptSubmit, PreToolUse and PostToolUse handlers; the latter two match Bash. Leave successful output empty so the host's ordinary execution and permission handling continue. Never return permission approval or updatedInput.

Only the exact declared command in the declared session cwd is managed. Its POSIX representation is `cd -- '<absolute action cwd>' && '<executable>' '<arg>' ...`, generated by `nativeActionCommand` from the validated task action with single-quote escaping. Preflight verifies that equality. Other commands, read-only context recovery, and user consultation bypass this gate. This is not a shell security policy or universal tool coverage; equivalent spellings and alternate tools are outside scope. Reference command timeout/output settings do not control host execution.

## Source and Request Wiring

1. Use [Context Preparation](context-preparation.md) for source review, explicit owner confirmation and separate worker read/ack. It emits the pinned `preflight` request, state and inert hook template without manual hash assembly. This operation repeats scoped source/review/capsule/readback checks without executing a command or recompiling.
2. Review the generated `context.hook-state.v1` with `{schema,request,eventBindings}` and the exact hook definition before opting into native setup. Request is `{path,sha256}`; the metadata directory already exists. These are local transport artifacts, not a second semantic graph. Switching an adopted adapter to a new packet is explicit and preserves prior evidence; common command use requires no native setup.
3. UserPromptSubmit stores one metadata record keyed by the hash of `{session,turn}`: prompt SHA-256 and an opaque transcript pointer, not raw prompt text. The adapter never scans the transcript. Same identity/content is quiet; conflicting content leaves a persistent conflict marker and requires owner reconciliation. Missing current input is UNKNOWN and blocks the managed action.
4. The owner reviews the actual source and supplies its existing source classification/integration and updated preparation as needed. A binding is `{eventKey,eventSha256,classification}`; classification is the exact existing `{sourceId,eventId,sha256,classificationSha256,reviewSha256}` binding. The adapter checks the original source body's SHA-256 equals promptSha256, independently of the caller's chosen classification. A materially new prompt cannot map to an unrelated old classification. Whole prompt identity is required; no regex atomization or automatic NO_CHANGE. The original transcript remains evidence; source export and semantic review stay owner responsibilities.
5. PreToolUse checks every recorded input for that session plus current turn visibility, then runs pure reference preflight. On success it records an admission and returns no output; **only the host invokes the original tool**. Source gaps deny only that exact managed command.
6. PostToolUse records the admission hash and response hash once, with acceptance NOT_ESTABLISHED. It does not rerun the action, retain response body, rewrite the tool result or infer success/acceptance. Delayed output can still record the original admitted action after new input arrives.

The reference source inventory, classifications and reviews remain the only semantic system. Metadata mapping establishes exact transport identity, not human authentication or interpretation truth. Undelivered prompts/history and removed metadata cannot be detected universally; keep the recorded window and its review evidence for the declared task.

## Concurrency and Recovery

An exclusive directory lock serializes short metadata transitions; bounded contention denies managed work without stealing locks. Atomic rename prevents partial JSON publication. A crashed lock or missing post observation needs explicit reconciliation. Never delete unknown admission/lock state just to retry a potentially executed action.

Admission identity is session plus tool_use_id, with turn and command binding. Repeated PreToolUse for that id is denied after admission; repeated identical PostToolUse writes no duplicate receipt. Conflicting post output reports a gap. This gives at-most-one admission per tool id, **not action-level exactly-once across different ids**. Multiple matching hook definitions can deny each other's duplicate admission; configure one copy. A host retry after admission but before execution may remain blocked even if no action ran; reconcile rather than guess.

Metadata input is bounded to 2 MiB, recorded events to 256 and directory entries to 1024. Retire a window only through owner-reviewed reconciliation, not automatic truncation. Current callbacks are synchronous; no timers, subscriptions or model requests are introduced. There remains a race after preflight returns and before host execution; hooks cannot make external actions atomic.

Malformed identifiable managed state returns an explicit PreToolUse deny. Unmatched actions do not read state. Known prompt-intake failures persist a session-scoped failure marker independently of the writer lock, blocking later managed calls until reconciliation. If even that marker cannot persist, UserPromptSubmit allows the message with a LIMITED/UNKNOWN warning so repair/stop consultation remains possible. Indistinguishable old state after total write failure is a residual gap, not a fail-closed guarantee. Unparseable callback input, hook startup failure, timeout, disabled/untrusted hooks or host coverage exceptions can leave the hook skipped: report coverage UNKNOWN, not universal enforcement.

## Verification and Adoption

`tests/context-hook.test.mjs` separates library preflight from subprocess callback-protocol tests. The protocol harness explicitly performs the harmless action outside the hook and is not a native session. It checks pending/covered input, source-body substitution, new input invalidation, malformed state, recovery, duplicate/concurrent callbacks, no raw-body persistence and no hook-owned command invocation.

An isolated native CLI test reviewed and trusted the exact definition through supported UI, then observed source rejection, an unrelated recovery read, one host-owned command, its post observation and duplicate-call rejection. A bounded replay exercised the generated preparation packet. These used a deterministic local provider, not real-model semantic evaluation. Reproduce applicable host evidence for project adoption; no trust-store edits or bypass flags. Desktop inheritance, full live history and product reliability remain unproven; CLI proof does not activate other tasks.
