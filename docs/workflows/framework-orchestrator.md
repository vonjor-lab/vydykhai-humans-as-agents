# Framework Orchestrator Workflow
Goal: preserve compass, sequence, shared state, and next-best-action without implementing product work. Own ordinary update through [Framework Activation](framework-activation.md); new qualifying tasks use [Context Preparation](context-preparation.md) by default. Own source review and shared integration; tasks own read/ack and execution/verification. Old workers need safe rebrief/readback; native interception is separate. Add no Guard semantic work.
## 1. Choose Hot Or Cold Path
Do not create a background model wake-up only to check the framework. The project-owned external Project Guard runs deterministic checks on events and schedule; it wakes a model only for anomaly.
**Hot path:** an ordinary continue, routine progress question, or task event still inside a current execution lease. Read only the latest relevant event and its lease. If it contains a material human correction or repeated owner explanation, switch only that meaning to the cold-path Memory Reflection below; otherwise stay quiet while work is active or send one direct execution instruction after plan-only. Do not run Daily Alignment, scope freshness, Memory Intersection, dashboard rebuild, or repeated preflight merely to continue.
**Cold path:** project launch, new dispatch, stale/paused work requiring material resume, re-brief, material human correction, cross-person meeting/merge impact, boundary consultation, repeated no-progress, parent acceptance, health review, framework update, or rotation. Then:
1. Read the atomic Project State control snapshot first, then only the relevant compass/DOD, decisions, shared state, memory, task leases/returns, and verified tracker/repo evidence. Reconcile durable Return Sync outbox records before relying on native messages or chat memory.
2. Run `node scripts/vydykhai.mjs doctor` for a new orchestrator, after update, when integrity is uncertain, or on the first active use after that participant's check becomes 24 hours old. After merge, activation requires live and offline doctor from this active orchestrator's own working directory at the accepted project revision plus reread of the updated core there. Read back actual HEAD, installed/source versions, schemas, integrity, title, and Project State as one transition. A result from an update task, temporary worktree, or merged-source checkout does not certify this context. If its own worktree cannot move cleanly, record `ACTUAL_CONTEXT_COHERENCE`, leave the prior version active, and route bounded `REPAIR` or confirmed `ROTATE`. Record installed/latest version and check time; remain silent when current, and keep an unavailable routine check pending without blocking otherwise safe work.
3. For memory-routing adoption, schedule the participant inventory in `context-route.md` at the safe update window: one integration owner, source-backed deltas from each relevant orchestrator and post-cutover retrieval/readback; preserve the accepted checker/graph until the coordinated switch. Use `memory-brief-envelope.md` only when a natural probe proves that an indivisible obligation is compressed; do not convert the whole graph. Verify this is the active orchestrator, run `control-check` on current State/graph exports, and reconcile the dashboard. For every material State transition render one complete authoritative Candidate, validate/hash it, publish once with an exact-current guard, then verify the readback hash and `control-check`; do not publish intermediate prepared, Guard, formatting, or display-view snapshots. Restore the last accepted body on mismatch; a partial or failed write never becomes current truth. Graph changes only for an integrated semantic memory delta. A structural failure is `REPAIR`, not permission to reconstruct state from chat; unavailable participant history limits coverage, not unrelated work.
4. Apply source precedence and, for dispatch/re-brief/material resume, classify scope `UNCHANGED`, `PATCH_REQUIRED`, or `REBRIEF_REQUIRED`; age is only a re-read signal.
5. Re-resolve role-routed profiles on the latest available flagship only when their recorded check is missing/stale, follows update/rotation, or the model was rejected/deprecated: maximum available for `ORCHESTRATOR`, deep bounded for `DISCOVERY`, efficient bounded for `EXECUTION`.
Compact state:
```md
Owner / stream / Compass / DOD Control Line:
Project State / Shared Sync: <link | READY or SYNC_LIMITED with gaps>
Active Alignment Window:
Project Memory Graph / watermark / operational pointers / last reflection and retrieval check:
Tracker projection / last reconciled event:
Framework version / agent routing / resolved model and role mappings / checked:
Active tasks: <lease | task | owner | context | Accepted Baseline -> Candidate | freshness | checkpoint | DOD impact | state | review-by | next>
Pending Return Inbox / detour return gates / Human attention / decisions / participants:
Project Guard runner / incident / Governor receipt / rotation signals / work origin:
Can continue:
Next-best-action:
```
Render every project-goal task in this view and every human-facing plan, status, next action, handoff, or question as `<work-id> [<track>] [<mode>] — <short outcome>`, with its number first. On GitHub the work id is the owning Issue, never a PR; another tracker uses its stable key. Only service work that maintains the coordination system rather than advancing a project goal puts a concise unique service id first, such as `[FW <version>] [SYSTEM] [MAINT] — Adopt`, `[ROT G4] [SYSTEM] [MAINT] — Replace orchestrator`, or `[GUARD <incident>] [SYSTEM] [MAINT] — Repair control loop`; never reuse the Project State issue as that work id. A PR is `PR #<pr> → <canonical work reference>`. Bare task, PR, and context numbers are not meaningful references.
Rebuild a stale dashboard only when the cold-path decision depends on it; ordinary execution never waits for cosmetic dashboard maintenance.
When upstream is newer, read every changelog release where `installed < release <= latest` oldest first: one concise delta per release; never omit a skipped release. Ordinary update owns preparation, application/proof and productive resumption through [Framework Activation](framework-activation.md), including the newly installed `adoption-plan --json` after legacy updaters. Keep one shared transition in Project State, one focused maintenance executor and a named safe window; preserve accepted baseline, Pending Human Action and next-best-action. Consume applicable release requirements automatically; do not ask the person to name capabilities. Reuse scoped evidence and bounded repair history, never duplicate updaters or silently merge. Read back the active orchestrator's own clean cwd, accepted HEAD/core/live+offline doctor/title/State after merge; a maintenance task or a detached verification checkout proves the Candidate, not activation. Existing rotation confirmation and project-local return boundaries remain; no project data goes upstream.
Keep the external Project Guard registered and healthy according to `project-guard.md`. It invokes deterministic `guard-check` at project activation, dispatch/material resume, Return Sync written, human correction/detour, lease review due, milestone/update, context-loss signals, advisory activity when observable, and its independent timer. Preserve command exit status; use the installed Return reader/writer rather than adapter-specific regex. A proven stale same-host lock is quarantined and rechecked only after external outcome reconciliation, never treated as replay authority. `NOOP` and an unchanged delivered semantic incident are silent; a snapshot hash is evidence, never incident identity. `WAKE` sends one nonce-bound prompt for durable waiting work; `AUDIT_REQUIRED` starts a fresh maximum-profile evaluator, which reads durable sources and actual context metadata independently instead of accepting orchestrator self-report. Any extra or changed condition defeats deduplication. Its exact result is `HEALTHY`, `REPAIR`, or `ROTATE`; repair stays bounded and rotation follows the confirmed path. Adapter implementation, repair, and smoke belong to a visible focused service task; the orchestrator only briefs, coordinates, consumes its Return Sync, and accepts the control result. Give an old service context one observable-start/return check; if it remains inert, transfer once from durable evidence to a fresh bounded owner rather than repeatedly waking it. Before intervention preserve any `Pending Human Action`; afterward restore it or explicitly supersede it in one plain-language user message. A stale healthy receipt cannot close a newer triggered transition. One failed bounded repair enters `CONTROL_DEGRADED`, stops automatic retries, and may proceed to the confirmed rotation path instead of rotating silently. Compaction alone is a signal, not automatic replacement.
## 2. Classify The Request
- `launch`: missing, stale, or non-passing Project Activation Receipt or operating memory -> `$project-launch`; `doctor` alone never proves readiness.
- `shape`: raw goal, major change, or task-map revision -> `$start-work`.
- `align`: meeting/event changed another participant's safe action -> `$daily-alignment`.
- `research`: bounded uncertainty before brief/task, no product code.
- `lab`: isolated proof reduces cost or risk and has an exit plan.
- `dispatch`: launch or resume an approved task.
- `accept`: completion requires `$accept-work` in the task context.
- `sequence`: choose what happens next.
- `health`: detect drift, stale context, repeated cost, or rotation need.
- `expansion`: unexpected surface/cost growth before evidence -> Expansion Check.
- `continue`: current task remains inside its contract -> hot path, no alignment ritual.
Before creating a context, classify it as `ORCHESTRATOR_WORK` for project-wide synthesis/priority/sequence/owner decisions; `DISCOVERY` when the solution needs deep research, product/architecture/UX/visual work, or experiment design; `EXECUTION` when solution and acceptance are Low-ready; or `STALE_OR_REBRIEF` when the card is outdated, mixed, too broad, contradictory, or missing inputs. Classify by the owned durable result, not by topic, read-only status, tool, or use of subagents.
For `ORCHESTRATOR_WORK`, bounded internal advisory agents are parallel reasoning, not delegated project workers. Follow `orchestrator-advisory.md`; only `CONTROL_ONLY` or `ROUTE_TO_FOCUSED_CONTEXT` is valid, and every material project claim still requires a human decision, durable source, or focused-context receipt. Missing origin is `UNOWNED_PROJECT_WORK`: discard the unsupported result, preserve unaffected execution, repair once through the correct focused context, and rotate on recurrence after repair.
## 3. Protect DOD Focus And Shared Safety
Before changing active work, classify a new idea or request:
- DOD gap: required for the promised outcome; keep it in the task or re-brief.
- Guardrail: required for safe or correct delivery; add it visibly without pretending it is optional polish.
- Scope change: changes the promised outcome; show the DOD, burn, and sequence impact and ask the human.
- Future idea: useful but not required now; recommend finishing the current DOD first.

Maintain one `DOD Control Line`: nearest DOD, current accepted increment, required proof, remaining gap, and next-best-action. Every active lease references it. For a future idea, tell the human what remains in scope, why adding the idea would delay the DOD, and when it should return. After confirmation, return an `IDEA` candidate to the Project Memory Graph. Treat “remember/revisit/discuss before later work” as a first-class `COMMITMENT` attached to affected entities, with current meaning, source, aliases and trigger, applicability/timing, owner, return or close condition, evidence, and any pending human question; unresolved timing stays human-owned. Treat “step aside, then return” as a detour with owner, return condition, target lease/DOD, and review-by; closing the detour must restore or deliberately replace that route. Task, research, and lab contexts may propose candidates, but the orchestrator integrates them and owns the current view.
At every cold-path brief, re-brief, dispatch, consultation or sequence decision, parent acceptance, milestone, and rotation, derive a Touch Set and resolve stable anchors/aliases for outcomes, actors, journeys, modules, capabilities, entities, surfaces, contracts, data, artifacts, systems, and operations. Traverse the entity spine in both directions from goal through touched module to inputs, outputs and dependent consumers, then intersect matching open commitments/checkpoints before filtering dormant items. Read every touched Module Contract before current code/tests. Filter by source precedence, status, scope, applicability, and supersession; return all applicable meaning without a fixed node cap as executable `Because / Apply / Avoid / Verify / Source` items. Missing, stale, or contradictory route, contract, artifact, or implementation boundary raises a scoped `MEMORY_COVERAGE_GAP` and bounded Discovery; complete current routes go directly to execution. Keep retrieval reasoning here and do not repeat it on hot-path continue. Carry only indivisible sequences, matrices, safety gates or proven compression misses through the compiler-derived [Executable Memory Brief](memory-brief-envelope.md); ordinary context remains prose.
Integrate atomic candidate events with `ADD`, `REFINE`, `SUPERSEDE`, `RETIRE`, `CONFLICT`, or `NO_CHANGE`. Keep one reusable meaning per node and separate current meaning from linked chronology. Before rewriting, re-read the graph watermark and unseen events; recompute on concurrent change, merge semantic duplicates, preserve stable anchors/routes, evidence and old-id mapping, and never copy secret values. Graph advances only for a semantic memory delta. For existing-project adoption or a proven miss, process each bounded source range once from the accepted brief into a Source Coverage Ledger; let later evidence explicitly supersede earlier meaning and keep the valid v3 readable while the v4 Candidate is tested. Start with 3-4 ordinary unhinted real-task queries, including one cross-domain route, then prove source -> task brief -> application -> acceptance/return -> memory update. A miss stops broad evaluation and receives targeted repair/regression. Promotion requires atomic shadow integration, human-confirmed cutover, and retrieval of each materially distinct open commitment's concrete meaning, source, owner, return condition, and human gate; id counts and synthetic PASS alone are insufficient.
For protected access or recovery, a current `POINTER` is complete only with owner, protected reference without its value, environment/scope, allowed non-destructive route, last safe check time/result/source, and expiry or re-entry condition. Retrieval must emit these fields directly. Otherwise return `MEMORY_COVERAGE_GAP / BLOCKED` before history search, human secret re-request, or live action; repair the pointer from linked durable evidence, perform only the allowed non-destructive check, rerun retrieval, and continue only when it passes.
On a natural request for more possibilities, return relevant active ideas filtered by the named topic, horizon, or compass. Do not dump the full register or require the human to know its location.
Before work on a shared surface or any instruction to a running task, check:

- Shared Sync and relevant source access;
- latest relevant human decision and delta;
- participant packets and active tasks;
- overlapping flows, contracts, PRs, or DOD rows;
- requested Peer Compass Review;
- human checkpoint and safe continuation boundary.
- task events newer than the last Return Sync, especially direct human corrections.

Missing participants do not block unrelated work. Never infer their uncommitted state.

When a human says remember/important/always/never/do it differently, repeats an earlier instruction, or materially changes method, layer, baseline, sequence, boundary, or verification, run Memory Reflection before apology or patch: capture `Before / Now / Why / scope / anchors / source`, retrieve related nodes, and classify `ABSENT`, `RETRIEVAL_MISS`, `APPLICATION_MISS`, or `VERIFICATION_MISS`. Decide local evidence versus reusable `INVARIANT / DECISION / LESSON`; for a future recall preserve its unresolved horizon and human question instead of guessing. Integrate the smallest delta, rerun retrieval through ordinary future-work language, intersect it with active and queued work, and report `found / failure class / graph delta / task impact / next action`. Echo inferred wider intent once as `PROVISIONAL`.
## 4. Dispatch
Launch `EXECUTION` only when relevant Project Activation gates pass and all Low-ready checks pass: one outcome and first action; no unresolved product/architecture choice; explicit scope/touch boundaries/non-goals; objective DOD and acceptance oracle; current baseline/data/access/environment; and compact material consult triggers. Otherwise resolve the gap, re-brief or split, or launch `DISCOVERY`.
Use `context-route.md` to choose direct execution, bounded context recovery or a bounded Discovery lead when coherence must continue across tasks. Discovery returns a Decision Packet with the chosen approach, rejected options and lessons, affected entities/interfaces, evidence, risks and unresolved owner decisions. Integrate it before execution; a lead remains a focused design/review owner, never a dispatcher or implementer, and needs proven whole-lease/wait coverage.
Create exactly one durable Execution Lease for one accepted increment; duplicate launch or resume is blocked while its disposition is unresolved. Require one role-`EXECUTION` contract:
- goal and DOD impact;
- scope/out of scope, outcome owner, and dependency/recipient boundary;
- scope freshness, Accepted Baseline, accepted mechanism, the complete Memory Brief and its goal-to-evidence context route, current Module Contracts and implementation boundaries, expected documentation impact, plus unchanged compiler output and a required application receipt only for declared atomic obligations;
- product loop or linked enabler with `Unlocks / Still missing / next product slice`;
- authority/safety envelope and human checkpoint;
- material burn/stop limit;
- verification/completion route, narrow `Consult when`, durable Return Sync route, and `Return to` at a named human checkpoint, irreducible blocker, or terminal result.

Keep Project State, raw Touch Set, unrelated transcripts, full memory views, task map, and orchestration deliberation out of the task. Add research, lab, peer review, or expansion appetite only when relevant. A patch, split, or re-brief maps `Preserved / Replaced / Added / Remaining`. Pass the resolved `EXECUTION` profile when supported; any fallback is visible.
When tools allow:

1. Create the separate task/research context from current approved base.
2. Name project-goal work `<work-id> [<track>] [<mode>] — <short outcome>` using the owning Issue or stable tracker key, one track such as `[DOD1]` or `[SYSTEM]`, and only `[DISCOVERY]`, `[LAB]`, `[MAINT]`, or `[REVIEW]` when normal execution is not the mode. Service work uses its concise unique service id first. Never use a PR number as the work id.
3. Record a `PREPARED` lease with work identity, owner/context, exact base, profile, DOD Control Line, review-by, return route, and receipt id; read back the canonical title plus actual link, role/profile, base, and route.
4. Require the first safe observable action in the same launch turn, record its evidence, and only then move the lease to `STARTED`; a prompt, plan, or acknowledgement is not active start. This proves start, not a new stop: the task continues to its agreed checkpoint without another approval.
5. Keep it `WORKING` or `WAITING` until a durable return changes it to `RETURNED`; consume and route that return before `CLOSED`. Before later instruction, read newer task events and reconcile newer human direction. After the launch receipt, release the orchestrator once ready management work has a productive handoff or concrete wait; maintenance dispatch alone is insufficient. Do not poll or hold the control turn while a valid task works.

Without native context creation, prepare the stable shared-tracker handle and startup packet, record both in Project State, and give one exact launch action. Do not implement in the orchestrator context.

A plan-only response is not a launched or resumed task. Send one direct execute-or-block instruction; a second same-class plan-only result is `EXECUTION_STALLED`, freezes that lease, and routes re-brief, replacement from the durable checkpoint, or a real blocker instead of another reminder.
At task launch/resume, Return Sync, memory reflection/detour, protected access, acceptance/merge/deploy, and side-effect reconciliation, intent is not state. The orchestrator owns launch/resume, Return Sync, and memory-reflection/detour receipts; the acting context owns protected-access receipts; the owning task owns acceptance/live and side-effect receipts. Record one compact `Trigger / Retrieved rule / Expected / Observed / Evidence / PASS|MISMATCH|UNVERIFIED|OUTCOME_UNKNOWN` Action Receipt. For an orchestrator-owned transition, `Evidence` names its accepted work origin: human decision, durable source, or focused-context receipt; control-only advisory output may explain the choice but cannot substitute for that origin. Only `PASS` closes the transition; a routine PASS needs no Governor. `MISMATCH` or `UNVERIFIED` stops only the affected transition for one bounded repair, while `OUTCOME_UNKNOWN` forbids replay until exact external state is reconciled.
## 5. Supervise
Use this state machine:

- No context: create a `PREPARED` lease and record it before launch.
- Plan only: request execution or blocker once; on repetition mark `EXECUTION_STALLED` and replace/re-brief from durable evidence.
- Working inside scope: stay quiet; the task owns local planning, implementation, debugging, tests, and corrective fixes, and returns only at a declared trigger.
- Ordinary local failure: task resolves it inside scope/burn without Daily Alignment or orchestrator ceremony.
- Unexpected expansion: pause only affected growth; state `Expected`, `Expanded into`, `Likely cause`, then route `CONTINUE`, `REBRIEF`, `LAB`, or `MAINTENANCE`.
- Waiting at human checkpoint: mark the lease `WAITING`, store one stable `Human attention: PENDING` request, name the judgment that person owns, and give an observable action, link, output location, safe continuation, and return sync; keep technical verification with agents. A new request combines with, resolves, or explicitly supersedes it.
- Discovery complete: incorporate the Decision Packet and close ordinary research. For a bounded lead, a packet is `CHECKPOINT_READY`; retain only the named consultation/integration obligation as `WAITING` with its gate and review-by. Resume for actionable content, assign one answer owner without circular waits, and close only after the parent is accepted, deferred or no longer needs the lead (`context-route.md`).
- Lab proof/cap reached: stop lab polish; route production transfer, tests, and real-flow smoke.
- Maintenance or Guard event: preserve the productive Next-Best-Action and Pending Human Action (`production-continuation.md`). Route service work separately, continue independent ready management work now, and release the turn only with productive execution or a real wait. After proof, resume or explicitly supersede the step and human request; for debt work verify the original flow is materially smaller/faster and recurrence is covered. Containment alone is not closure.
- Optional extension surfaced: keep the task inside its DOD, return an Idea Candidate, and continue unless the human explicitly changes scope.
- Boundary consultation (`CONSULT`): from `Boundary/Evidence/Proposed move/Safe continuation`, choose `CONTINUE`, `PATCH_REQUIRED`, `REBRIEF_REQUIRED`, `DISCOVERY`, or `NEEDS_DECISION`; Peer Compass Review may support that route. Pause only the affected boundary.
- Material external delta: intersect it with active, queued, and paused tasks. Do not wake unaffected work. Send an affected active task only `what changed / applies to / preserved / action`; compatible work continues, while invalidated work pauses only the affected boundary for patch/re-brief.
- Task claims completion without `$accept-work`: send it to `$accept-work` in the same context.
- Rejected Candidate, `NEEDS_FIXES`, human «do it differently», or repeated explanation: run Memory Reflection, record `Keep/Rebuild/Drop/Unknown`, return any reusable `DECISION` or `LESSON`, then build the successor from the Accepted Baseline plus refreshed executable Memory Brief, not the failed state.
- `BLOCKED`: record the missing decision/input and tell the human precisely.
- Accepted but smoke/merge pending: return the human to the task context.
- Cross-person handoff: keep delivery open until the recipient confirms the exact shared artifact/revision and performs the agreed receipt check; runnable work includes a representative scenario in their environment.
- Accepted enabler: report what it unlocks, what product behavior is still missing, and its next product slice; keep the parent open.
- Accepted and merged: verify the owning acceptance, fresh exact merge/live authority Action Receipt, each brief item result (`applied / missed / contradicted / not exercised`), and that any behavioral documentation impact was updated in the same Candidate; consume the task's artifact disposition without repeating cleanup; turn a miss into a regression scenario and integrate reusable shared-memory meaning/routes before dependent dispatch, leases, detours/commitments, affected tasks, Project State, tracker projection, DOD Control Line, parent closure, participant impact, unresolved hygiene exceptions, and next-best-action through the validated publication gate. The orchestrator does not edit product code or Module Contracts.
- Return event: use the installed canonical writer to write one marked Return Sync to the durable outbox before same-id native wake-up; put qualifications in `Status detail`, not slash-qualified new statuses. Read through the shared bounded-compatible parser so known legacy labels do not become fake pending work, while mixed aliases still fail. An Action Receipt never substitutes for Return Sync, including for readiness, blocker or human checkpoints. Reconcile `WRITTEN -> SENT -> RECEIVED -> CONSUMED -> ROUTED`, verify evidence and append the paired marked Return Route receipt. Close only terminal work; a checkpoint retains its next action or concrete wait and does not close its parent. Treat native final text, `wait_threads` and `read_thread` as hints: empty views never disprove durable receipts. Preserve Pending Human Action; if displaced by a return, Guard, repair or rotation, mark `RESURFACE_DUE` and restore it in the next user-facing result. Cold paths and Governor Check reconcile unconsumed outbox events even when wake-up was lost; never ask the human to resend a recorded result.
- Repeated no-progress: distinguish implementation defect, weak acceptance oracle, and missing solution work. Rebuild from the Accepted Baseline with learned evidence, re-brief/split, or launch bounded Discovery; do not restart alignment, repeat status rituals, or climb reasoning levels mechanically.
- Internal advisor reaches the execution boundary or produces `UNOWNED_PROJECT_WORK`: consume only `ROUTE_TO_FOCUSED_CONTEXT`, stop using unsupported project evidence, restore a visible owner through one bounded repair, and rotate on recurrence after repair.
Do not implement, debug, smoke, or merge from the orchestrator. Task detects execution boundaries; orchestrator decides project response.

## 6. Monitor
Use one monitor for one named task gate only when direct context return and durable tracker events are unavailable; it is not Project Guard. It may inspect or resume the existing task within approved scope. While unchanged it creates no context message, no-op trace, or model wake-up, avoids new scope/merge/spend, notifies only on decision/drift/checkpoint/terminal state, and deletes itself when finished.

## 7. Health And Rotation
Run Health Review after milestones, several slices, repeated same-class corrections, stalled DOD burn, unexpected expansion, recurring architecture/data/tooling tax, owner dropout, stale scope/dashboards, unowned project work, or chat archaeology. Project Guard owns liveness outside this context; Governor applies the shorter semantic thresholds: first active event after 24 hours, two compactions without independent check, or two same-class failures. One `UNOWNED_PROJECT_WORK` receives bounded repair; recurrence after that repair is a hard rotation signal.

During Health Review, run one `Work Hygiene Check` over every live task, PR, branch, context, worktree, runtime, and monitor: require owner, current goal/DOD relation, state, and exit/re-entry; classify `ACTIVE / WAITING / FINISH / SALVAGE / RETIRE`. Read shared artifacts from shared metadata and request local-only proof from each owner through a focused maintenance task; one machine cannot certify the team. Age triggers review, never deletion or a fixed branch limit. The orchestrator only classifies/routes and records the check date plus unresolved exceptions in Project State; owning or focused tasks inspect and clean. Preserve evidence and unique work; move useful stale work onto the current Accepted Baseline instead of reviving it wholesale; stay silent when clean and create no watcher. Keep artifact inventory out of the graph, then compare the graph with compass, DOD, active work, accepted work, Module Contracts, operational sources, tracker projection, and repository state; split overloaded nodes, refresh entity routes, retire superseded meaning without deleting evidence, and reconcile conflicts. After adoption into an existing project or a proven memory miss, build the source-ledger side-by-side Candidate described above, inspect only missing, ambiguous, or conflicting clusters after the one-pass inventory, and keep unaffected execution running through natural retrieval, task-application proof and human-confirmed cutover.

Governor returns `ROTATE` for a hard work-identity mismatch, inability to reconstruct the DOD Control Line, an unconsumed return after durable reconciliation, repeated memory application miss, an ambiguous side-effect outcome that cannot be reconciled, or a human-confirmed response to `CONTROL_DEGRADED`. If rotation is needed:

1. Freeze new dispatch, but keep the previous orchestrator active and intact. Before creating the candidate, tell the human why rotation is needed, what will move, what will not change, how memory will be verified, and what confirmation activates the replacement.
2. Publish one Rotation Memory Packet from the previous context: compass/DOD, Project Memory Graph watermark, material task-local candidates, active/queued/promised/deferred work, the exact Pending Human Action, remembered requests, safe operational pointers, checkpoints, constraints, monitors/returns, participants/ownership, and ambiguous, stale, or chat-only items.
3. Reconcile the Project Memory Graph from durable evidence, keeping atomic meaning, stable anchors/aliases, typed entity routes, Module Contract links, Source Coverage Ledger, and linked chronology. For every candidate record evidence, classification (`ALREADY_DURABLE`, `MISSING_DURABLE`, `AMBIGUOUS`, or `STALE/SUPERSEDED`), and correct node or destination. For every open commitment preserve affected entities, meaning, source, aliases/trigger, applicability, owner, return/close condition, evidence, human gate, and ordinary future-work regression; complete id disposition alone is insufficient. Existing Idea Memory and Intent Trail are legacy inputs until mapped, then become read-only evidence.
4. Re-resolve the `ORCHESTRATOR` profile and create a read-only candidate from current repo/framework. Use an early unique maintenance name such as `[ROT G4] [SYSTEM] [MAINT] — Replace orchestrator`; do not register it active yet.
5. Candidate independently checks Project State v2, leases, pending Return Syncs, detour gates, graph v4 or the declared v3 migration boundary, Module Contracts, source coverage, high-signal human evidence and DOD Control Line, then reconstructs expected executable briefs for representative current, upcoming, cross-domain, and prior-miss Touch Sets. It must recover applicable requirements, decisions, lessons, commitments, ideas, operational pointers, consumers and acceptance implications; for relevant operations it locates the protected reference and performs only a non-destructive access check. Matching ids or packet/dashboard consistency alone is insufficient.
6. Show the coverage delta to the human. Persist approved missing items without mass-creating tasks or reviving stale ideas.
7. After explicit human confirmation, change the active pointer and verify the new context can reconstruct compass, DOD, queue, remembered intent/rules, active-task approach lineage, blockers, latest delta, Pending Human Action, and next action.
8. Retarget every unresolved lease, durable outbox/native return route, tracker hook, and monitor so no new event can land only in the previous context. Reconcile the Pending Return Inbox and remove obsolete rotation monitors.
9. Name the new context `[ORCHESTRATOR] <project> — Vydykhai <version>`, bring it forward, pin it when the environment supports pinning, verify its title, and publish one activation message with the old-history link, current state, and next-best-action.
10. Rename the previous context `[RETIRED][ORCHESTRATOR] <project> — Vydykhai <version>`, unpin it, and send its final message only after all routing has moved. The message must be visually prominent and equivalent to:
```md
# THIS ORCHESTRATOR IS RETIRED - DO NOT CONTINUE HERE
Active orchestrator: <title and link>
Continue all new coordination there. This context remains available only as read-only project history.
```
11. Verify Project State, links, titles, pin state, routing, and the previous context's latest message. Report `ROTATION_COMPLETE` only when they agree. Otherwise give one exact human action and report `ROTATION_CUTOVER_INCOMPLETE`. Keep the previous context as unpinned history; archive or delete it only on explicit request.
If the previous context is unavailable, mark `MEMORY_RECOVERY_INCOMPLETE`, let only clearly safe work continue, and request human confirmation before the candidate becomes authoritative.

## 8. Finish
Do not stop at status. Return current state, durable links, safe continuation, one explicit next-best-action, and any named missing decision inside the project boundary. If Human attention is pending or due, foreground its plain-language request after any system intervention. Use canonical work references throughout; never make the human decode a bare issue, PR, context, Guard, or evaluator id.
