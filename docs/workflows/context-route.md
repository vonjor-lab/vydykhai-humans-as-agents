# Context Route

Goal: each increment understands why its part exists, preserves applicable prior decisions and leaves verified understanding for later work. Completeness comes before context length. A narrow execution responsibility does not mean shallow product understanding.

## One Map, Existing Sources

Use the existing Project Memory Graph to navigate the accepted goal/brief, product journeys, architecture/contracts, modules, entities, decisions, accepted artifacts and verification. Do not create another source of truth or copy every source into every level. Graph v4 has two connected layers: stable entity anchors and routes provide navigation; atomic memory nodes provide current requirements, decisions, lessons, commitments, ideas, and safe pointers. Use canonical ids in current relations; retain old ids in the Legacy Source Map.

A part may serve several outcomes. Preserve its applicable parent requirements and affected upstream/downstream consumers; do not force all dependencies into one tree. Keep one canonical route direction and traverse it both ways: composition, purpose, inputs, outputs, persistence, prerequisites, and constraints are enough; do not add inverse or topic-similarity edges. Sources remain authoritative within their scope; a recent local experiment does not silently replace an accepted product-wide decision. Distinguish accepted meaning, provisional inference, bounded exception, future intent and superseded history.

## Entity Spine And Module Contracts

Resolve every cold-path Touch Set through this vertical spine:

`goal/brief -> outcome/journey -> module/capability -> entity/contract/data/artifact/system -> current meaning -> accepted artifact/verification -> current work/return condition`.

An anchor is a stable navigation address across human language, UI labels, code names, and historical aliases. A memory node is one independently applicable and supersedable assertion about one or more anchors. If one clause could change without the others, keep separate nodes. A recall commitment must attach to affected anchors and retain its owner, trigger/checkpoint, return or closure condition, evidence, and source; an unlinked “remember this” note is invalid.

Every durable module and capability links a current [Module Contract](module-contract-template.md). For any task that touches one, read in this order: relevant graph route and memory nodes, current Module Contract and linked specification, then current code and tests. Documentation is a prepared map, not proof that the code still agrees. A mismatch among graph, documentation, accepted behavior, and implementation is a scoped `MEMORY_COVERAGE_GAP`, not permission to trust whichever source is easiest.

## Three Routes

1. **Execution:** resolve the changed module/entity/capability, ascend to its purpose and applicable brief/architecture constraints, then inspect inputs, outputs, persistence, related consumers, open commitments, prior decisions, module documentation, rejected approaches and accepted artifacts. Reuse what exists before proposing a replacement.
2. **Discovery:** start at the desired actor outcome and descend through scenarios, responsibilities and affected entities. Compare candidate choices with the accepted architecture and prior rationale; return the decision and impact, not an implicitly authorized implementation.
3. **Correction and acceptance:** locate the level where understanding changed; compare intended and actual touched entities, preserve or explicitly supersede decisions, inspect affected tasks/consumers, and connect observed results back to the original outcome. Preserve why a rejected attempt failed without making it the next baseline.

Intersect open recall commitments and return checkpoints on every route. Follow applicable obligations until coverage is complete, not until a fixed hop or node count is reached. Filter unrelated and superseded material, but do not drop an obligation merely because it ranks below a topical match. If evidence is unavailable or applicability conflicts, record the exact `MEMORY_COVERAGE_GAP`; do not invent a parent, claim that all history was reviewed, or stop unrelated authorized work.

An empty local view does not establish that an accepted capability or its data never existed. Before requesting replacement input or proposing a rebuild, distinguish not found here, inaccessible source, incompatible projection/consumer, and verified loss. Trace accepted artifacts and safe source/version/environment references through current consumers; recovery preserves existing meaning and identifiers unless a separate change is authorized. Historical access is not live-action authority.

## Choose Preparation Depth

At shaping, material re-brief or a Discovery return, the orchestrator chooses preparation; the person need not know the modes. Ordinary continuation does not repeat this choice.

- **Direct execution:** the relevant vertical and consumer routes, Module Contracts, accepted baseline, current code and verification are current and the solution is Low-ready.
- **Bounded Discovery:** a route, source qualification, Module Contract, accepted artifact, or current implementation is missing, stale, contradictory, or unproven; the request restores prior behavior; or several modules/systems create material unreviewed consequences. Recover the necessary understanding once, then return it. Age, file count or task length alone never requires research.
- **Discovery with a bounded lead:** several execution tasks share one accepted outcome and decisions must remain coherent as their results arrive. Name the concrete cross-task obligation that a one-time brief cannot cover. A fresh large change can qualify; an old small task need not. If this need is uncertain, let bounded Discovery establish it first.

Use existing scope, dependencies, decision owner, burn/stop, checkpoint and Return Sync fields. No new role, permanent department, graph or scheduler is introduced. A lead uses the existing deep `DISCOVERY` profile and a normal work-id-first Discovery title; implementation remains efficient `EXECUTION`. Record the lead assignment and covered work in the parent brief, Execution Lease, and tracker projection, not a separate registry.

## Lead One Bounded Change

The lead owns the solution's coherence, not project management. Its Discovery brief names the parent outcome, preserved obligations, covered tasks, allowed design decisions, integration evidence, review limit and exit; project-wide orchestration/alignment instructions and executor-only startup steps do not become its duties. It prepares a source-backed Decision Packet and task-map proposal, answers material content questions, and reviews the combined result. It may resolve design details inside delegated scope; changed shared contracts, priorities, acceptance promises, spending and safety authority return to the orchestrator or named human owner. It never launches implementers, edits shared Project State/memory, implements product code, or becomes the implementation acceptance owner.

The orchestrator alone dispatches, changes active task contracts and integrates accepted memory. Each executor keeps one owning context and the same durable return route to its orchestrator; a lead is a named consultation/review recipient, not an extra mandatory relay for every result. Route only results that change its solution or satisfy a named integration checkpoint. Concrete tests, lab work and technical acceptance remain in their owning focused tasks; the lead assesses their implications rather than repeating them.

A Decision Packet is a checkpoint, not completion of a lead's parent outcome. Return it with `CHECKPOINT_READY`, evidence and the next dependency; after consumption keep the existing lead lease `WAITING` with a concrete return condition and review-by. Resume that context only for an actionable question, material correction or integration result, with a first-action receipt. Available for consultation does not mean continuously `WORKING`. A consultation assigns a next action to the lead while the requester waits only at the affected boundary; do not leave both waiting on each other. One failed bounded consultation returns the unresolved choice to the orchestrator for re-brief, another focused opinion or a real human decision, not repeated reminders.

Use the existing [Production Continuation](production-continuation.md) whole-lease observation before claiming protected leading mode: it covers the lead and executors, detects idle work and circular waits, and distinguishes them from real human/dependency waits. If the adapter cannot establish that coverage, use bounded Discovery plus ordinary tasks, explain the limitation once, and do not simulate a supervised lead. Respect harness creation, messaging, approval and visibility limits; when a separate-task launch requires a human action, give that action instead of claiming launch or substituting hidden workers.

Before compaction, replacement or an accepted design checkpoint, preserve sources, rationale, decision status and remaining obligations durably. Repeated correction, missing rationale or unexplained drift routes a fresh focused review; the lead cannot certify its own recovered understanding. Guard/Governor retain their existing control roles and do not acquire domain leadership. During orchestrator rotation, retarget lead and executor returns together and retain pending consultations and human questions. A stalled lead is repaired or replaced from evidence through the existing task path, not kept alive indefinitely.

Close the assignment when the parent is accepted, explicitly deferred or no longer needs cross-task coherence. Return final coverage, remaining obligations with owners, memory candidates and artifact disposition; the orchestrator consumes them, closes the lease and archives the context when supported. Ending a research phase, receiving a child result or merging one task does not close the parent. An optional improvement remains an idea rather than a reason to prolong leadership.

## Explain The Work

At a meaningful transition, explain the goal, why this preparation is needed, the next observable result and whether the person needs to act. Use ordinary product language and existing task names; do not narrate leases, receipts or internal slicing. Explain once at launch, then report decisions, verified progress, changed expectations or real blockers, not recurring no-op status.

- Discovery: "I will first recover the earlier decisions for this area so we preserve what already works. Then I will propose the smallest change."
- Lead: "This change spans several user journeys. I will assign one person or agent to keep the solution consistent across the work; the first checkpoint is the agreed scenario map."
- Progress: "The existing behavior is preserved in these paths. This remaining path needs a decision before we can finish; the other work can continue."

The orchestrator remains the person's primary contact. Direct discussion with a lead is optional; read newer human direction before sending instructions, preserve its scope and source, and reconcile affected work before claiming agreement. Keep one foreground Pending Human Action; other unresolved questions remain attached to their tasks and are not silently discarded. After a service event or rotation, restore the unanswered request or explicitly supersede it using the newer human decision. Do not make the person relay agent messages or decode technical identifiers.

## Existing Brief And Return

The orchestrator records the route inside the existing Memory Brief: goal/brief -> affected journey/module/capability -> inputs, entities, contracts, data, artifacts and systems -> current requirements/decisions/commitments -> consumers -> accepted artifacts and verification, with source revisions or checked evidence and explicit remaining gaps. Include actual meaning and rationale, not ids or links alone. Add the current Module Contracts and implementation boundaries for every touched durable module or capability. Consult original dialogue or artifacts when a summary cannot establish a material qualification. The task receives and reads the complete relevant context and source excerpts; unrelated history and orchestration deliberation stay outside it.

When one omission, merge or reorder would invalidate an exact sequence, path matrix, safety gate or previously missed obligation, carry only that indivisible part through the [Executable Memory Brief](memory-brief-envelope.md). Its compiler-derived ids and digest must reach the task unchanged, and the task must return a valid application receipt before claiming use. Keep ordinary rationale and safely factorable guidance as readable prose; the envelope does not replace this route, the graph, source review, acceptance or action authority.

Completion means that purpose, inherited constraints, dependent consumers, existing implementation and material conflicts have been examined. There is no seven-node or two-hop ceiling. If the full relevant context cannot be processed reliably, stage its preparation or rebrief at a meaningful boundary while preserving obligations; never silently truncate them. Ordinary continuation reuses the current route. Relevant source/contract changes invalidate affected portions, not the entire project.

The owning task verifies the changed boundary and affected consumers against its contract. A fixture, source repair or isolated component test is not evidence for unexercised data, runtime, recipient or end-to-end behavior. When behavior changes, update affected Module Contracts in the same Candidate. Return item-level applied/missed/contradicted/not-exercised results, actual scope delta, observed evidence, exact documentation changes, and a memory candidate or `NO_CHANGE`. The orchestrator integrates only accepted shared-memory meaning and routes after acceptance; it does not repeat execution or edit product/module documentation. Safety, authority, protected-pointer and human-acceptance gates remain unchanged.

## Separate Four Checks

- **Source accounting:** inventory bounded ranges independently of MEM ids before preparing a brief. Every observed event revision needs reviewed assertions/dispositions or explicit reviewed `NO_CHANGE / EVIDENCE_ONLY`; an unclassified range remains pending. State the inventory's scope and unavailable-history limit. A source omitted from both inventories cannot be discovered by comparing them.
- **Structure and delivery:** `control-check` rejects missing node meaning/anchors, dangling or untyped relations, duplicate fields and invalid retrieval-result columns. Plain or bold canonical labels have the same identity. The executable envelope binds supplied bytes and ids; neither check certifies original-source completeness or correct interpretation. A legacy field layout needs source-backed reconciliation, not invented lost knowledge.
- **Meaning:** before first use of a materially changed shared contract, migration or rotation, a fresh evaluator reconstructs the relevant route from original sources and ordinary task language, without being given the expected node list. Compare expected obligations with the brief; missing relevant intent is a miss even when all links resolve. A recorded `PASS` without this evidence is not semantic coverage.
- **Behavior:** the owning task proves actual changed behavior and preservation of relevant existing behavior. Independent source review cannot replace these tests, and green local tests cannot replace a missing cross-boundary check. Reuse current evidence where its source and scope still match.

## Bounded Reference Caller

The supported [preparation command](context-preparation.md) builds request files from ordinary source exports and explicit semantic decisions. The owner confirms the exact plan; the worker separately reads and acknowledges the context. This common path requires no hooks. For a task requiring `retained-progress-v1`, use the one-shot entry:

```sh
node scripts/vydykhai.mjs context-run --input <context-request.json>
```

`scripts/context-run.mjs#runContextTransition` owns intake, `checkPreparedContext` from `scripts/memory-brief.mjs`, and dependent/verification command invocation. Its additional `preflight` operation follows resume checks but returns READY without executing anything or compiling. The opt-in [lifecycle adapter](context-hook-adapter.md) uses that pure path before one declared host-owned action. Neither path writes shared meaning or interprets sources. File snapshots and tested callback protocol do not prove native adoption, complete history or fresh-worker semantics. Arbitrary tools can bypass this path; no provider, watcher or model callback is added. Guard retains control/delivery and does not run this path on a timer.

### Owners And Operations

The existing coordination-input owner names a source-set independently of the graph. The reader enumerates actual bounded files; the orchestrator or bounded Discovery reviews their meaning/dispositions. Executors propose corrections and own code, Module Contracts and verification. Only the orchestrator chooses/writes shared meaning and persists source/integration receipts in the existing ledger/outbox.

| Operation / caller | Required path and output |
| --- | --- |
| `prepare` / orchestrator at start-work | Read sources/relevant dependencies; verify source reviews and shared readback; compile atomic content only when supplied; bind every required assertion to actual advisory text or compiled clause/row; verify memory review. Return `PREPARED` capsule, no command. |
| `resume` / owning task at safe start/resume | Reuse pinned capsule without recompilation; refresh bounded sources/dependencies and worker readback. Then invoke the explicit accepted task command. Return `ACTION_COMPLETED` with command identity/output hash. |
| `accept` / owning task's accept-work | Same context gate; execute accepted verification script on declared Candidate files and retained-plus-new example plan. Require every observation, frozen oracle binding and unchanged Candidate/input hashes before/after execution. Return `VERIFIED`, evidence and marked Return Sync; not human acceptance or parent closure. |
| `integrate` / orchestrator after its shared write | Read source classifications, pinned orchestrator plan and actual shared artifacts. Return integration receipt only when approved hashes match. No commands/shared writes. Persist receipt and update relevant classifications before dependent preparation. |

All operations perform intake. Missing source/classification or unintegrated assertion blocks its scope even when Graph ids and Return routing look complete. `observed` events differ from `classifiedPrefixes`: the latter cannot cross an unintegrated event in that source. Explicit reviewed `no_change / evidence_only` records with zero assertions can advance source accounting without a Graph write. Neither cursor is the semantic Graph watermark. Persist receipts through Source Coverage Ledger `Checked`/existing artifacts; loss before persistence requires a bounded re-read, not skipping an event.

A reviewed local correction declares both `localOwner` and `localTask`. A pinned task with `allowLocalOverlay: true` may verify it only when **both** identities match. Other tasks wait for integration even when they share a worker. Acceptance Return identifies pending source deltas; paired Return Route does not satisfy shared readback. This avoids requiring global acceptance before task-owned verification.

### Reference File Contracts

JSON schemas reject extra/duplicate keys and malformed refs. A `ref` is `{path,sha256}` over actual file bytes, with workspace-relative paths, no traversal/symlinks and a 2 MiB file limit. The request names a canonical absolute workspace; its pinned task names the same root and matching identity file. Pins establish identity, not human authorization or truth: reviewed task/source artifacts remain trusted inputs under source precedence. The runner does not invent or authenticate a human review.

| Schema | Fields after `schema` |
| --- | --- |
| `context.request.v1` | `operation`, `workspace`, pinned `task`, nullable pinned `capsule/readback/integrationPlan`. Prepare: last three null; resume/accept: capsule+readback, null plan; integrate: plan, null capsule/readback. |
| `context.task.v1` | `id`, `owner`, `workspace`, pinned `identity`, `requiredCapabilities`, `enforcement`, `scope`, current paths `sourceSet/classifications/dependencies`, pinned `module/memoryReview`, `memory`, explicit `action`, `newExampleIds`, `candidateFiles`, `allowLocalOverlay`. |
| `context.sources.v1` | `sources: [{id,path,scope,kind}]`. `events` kind reads `context.events.v1` with `complete: true`, `events: [{id,authorKind,body}]`; `return` reads one valid marked Return Sync through the canonical parser. Incomplete visibility is LIMITED. |
| `context.classifications.v1` | `records: [{sourceId,eventId,sourceSha256,eventDisposition,assertions,reason,localOwner,localTask,review,integration}]`. Review pinned; integration null or pinned receipt. Event disposition is `assertions/no_change/evidence_only`. Event SHA hashes canonical `{id,authorKind,body}`; intake also hashes whole range bytes, preserving order/revision changes. |
| Assertion | `{id,disposition,scope,targetRef,reason,supersededBy,ownerGate,trigger,sourceRange}`. Scope must fit declared source scope. Disposition: `current_constraint/accepted_capability/deferred/superseded/unresolved/evidence_only`. Range: `{start,end,sha256}` over a nonempty UTF-8 byte excerpt. `supersededBy` resolves to an available reviewed assertion id; every edge must cover the full old scope, without self/cycles or unresolved targets. Partial replacement requires explicit scoped splits; deferred recall requires owner+trigger. |
| `context.source-review.v1` | `classificationSha256`, `reviewer`, `decision: approved`. Hash covers classification record excluding `review/integration`; changing source excerpt, meaning, scope or local authority invalidates approval. |
| `context.dependencies.v1` | `dependencies: [{id,path,scope}]`. Include relevant incoming/outgoing route projection, module/data/environment/authority dependencies. Only scoped entries are read; missing/new/revised relevant entries invalidate capsule. Undeclared dependencies remain a limit. |
| `context.module.v1` | `publicBoundary`, `implementationFiles`, `retainedExampleIds`, pinned `oracle/verificationScript`, explicit `verificationCommand`. Compact metadata referenced from the existing Module Contract, not another graph. The task's selected public boundary must match. |
| Task `memory` | `{publicBoundary,items,atomicInput}`. Advisory items: `{id,text,sourceAssertionRefs}`; atomicInput null or unchanged compiler input. Atomic clause/row sourceRefs name independently classified assertion ids. An id list cannot substitute for present rendered content. |
| `context.memory-review.v1` | `reviewer`, `decision: approved`, `sourceDigest`, `meaningDigest`, `contentDigest`, `publicBoundary`. Binds source/disposition projection and actual render; hash validity does not prove semantics. |
| `context.readback.v1` | `worker`, `taskSha256`, `capsuleSha256`, `capability`, pinned `evidenceRef`. Bound to actual task/capsule bytes; orchestrator version is not worker readback. |
| `context.integration-plan.v1` | `owner: orchestrator`, pinned `reviewRef`, `sourceBindings: [{sourceId,eventId,sha256,classificationSha256,reviewSha256}]`, `artifacts`. Classification hash uses the source-review projection; review hash pins exact review bytes. `reviewRef` is `context.integration-review.v1` with `reviewer`, `decision: approved`, `planSha256` hashing the entire canonical plan excluding only `reviewRef`. Resulting `context.integration.v1` contains pinned `plan` and its exact sourceBindings/artifacts; changed interpretation/review requires new integration. |
| `context.oracle.v1` | `examples: [{id,sourceAssertionRefs,input,expected}]`. Freeze source-derived expectations. Required ids are module retained ids plus task promised new ids, never the Candidate's observation list. |
| `context.observations.v1` | `candidateSha256`, `oracleSha256`, `observations: [{id,observed}]`. Script output; missing/extra/duplicate observations, wrong binding or expected-value mismatch fail. |

Source/meaning digests use canonical JSON/SHA-256 over sorted source records/range hashes and classification bodies; API/tests specify exact projections. Source scope includes unknown/unclassified meaning until reviewed; a source omitted from **both** source-set and inventory stays UNKNOWN. Local exports do not prove complete/recent live host visibility.

Integration artifacts use whole-file refs or `{path,sha256,startMarker,endMarker}`. Both markers must occur exactly once; hash the inclusive segment. Scoped sections of the one shared Graph/contract avoid invalidation by unrelated sections. The orchestrator's plan must cover actual accepted meaning: hashing a convenient unrelated segment is not semantic evidence. Historical envelopes and their whole-Graph authority hashes remain unchanged.

Commands are explicit accepted task-contract `{executable,args,cwd,timeoutMs,maxOutputBytes}`: absolute executable, canonical workspace-relative cwd, no shell strings or source-text commands. Known shell interpreters are rejected. Timeout is at most 60 seconds, output at most 2 MiB; failures preserve invocation counters and never dump stdout/stderr/source bodies. This is not a network/security sandbox for arbitrary approved programs. Verification requires its pinned script as the first argument. It receives `VYDYKHAI_CANDIDATE_SHA256`, `VYDYKHAI_ORACLE_SHA256`, JSON `VYDYKHAI_REQUIRED_EXAMPLES`; inherited environment is limited to PATH/SystemRoot/TMPDIR/TEMP. Candidate identity covers exact declared files/root, including all declared implementation files; it does not claim to hash an entire repo or undeclared imports. Reviewer establishes boundary and test adequacy.

CLI JSON reports evidence and actual read/compile/command counts. Exit 0: operation succeeded within the reference boundary; 1: BLOCKED; 2: LIMITED. Failure after dependent invocation retains `actionOutcome: OUTCOME_UNKNOWN` and requires reconciliation before replay. The file adapter reports only `enforcement: reference`; caller cannot self-promote to host or disable pinned capability via flags. Legacy readers remain valid but cannot silently satisfy a newly declared gate. Unchanged resume has no historical/model reconstruction or envelope compile. Relevant readback precedes invocation; external changes after that boundary cannot be made atomic by this tool.

`tests/context-run.test.mjs` uses real temporary exports, reviewed artifacts, local commands and Candidate verification through the CLI. Frozen fixtures in `tests/fixtures/retained-progress/` supply expectations independently of Graph. Ordinary preparation and one trusted native CLI command were also exercised with a deterministic local provider; see [adapter evidence and adoption limits](context-hook-adapter.md#verification-and-adoption). Fresh-worker interpretation, desktop inheritance and real product observation remain unproven. Historical fixture evidence labels describe their original scope, not later adoption proof.

## Existing-Project Inventory

1. Retain the exact current graph, accepted brief, decisions and artifacts as rollback evidence. Build one Source Coverage Ledger from the earliest accepted brief through the current watermark across accessible human dialogue, meetings, tasks, participant packets, PRs, code and accepted artifacts. Bound every source by stable id and revision so it is processed once; reread only changed ranges and explicit gaps.
2. Have one separately scoped focused reconstruction task build the stable entity spine first: outcomes/journeys, modules/capabilities, entities/contracts/data/artifacts/systems, composition, inputs/outputs, persistence, dependencies, and consumers. In the same reviewable Candidate, create or repair Module Contracts for durable modules and capabilities. Do not promote a temporary helper or incidental file into the product map.
3. Invite each relevant participant's orchestrator through the agreed shared sync route to reconcile its task-local decisions, human corrections, deferred insights and accepted artifacts against the same baseline. Each publishes its own source-backed delta or explicit no-change/coverage gap; one machine cannot certify another's private history. Share approved meaning and safe references, not private transcripts or secrets.
4. In that focused Candidate, attach atomic current nodes to the entity spine. Let later evidence explicitly supersede earlier meaning; split mixed scopes; preserve open commitments with return conditions; show preserved/added/refined/superseded/unresolved meaning and provenance. Do not delete historical evidence or read secret values.
5. Start with cheap fresh actors using ordinary unhinted real-task questions: current work, immediate next work, one cross-domain consumer route, the latest representative miss, and one sufficient-context control. Compare against independently established expected obligations. Then carry the retrieved brief through a disposable or read-only task application and Return Sync, and replay its accepted memory update. If any required link is missed, stop before broad evaluation, repair only that route, and rerun the narrow natural witness. If the miss is caused by compression of an indivisible obligation, compile that portion into the executable envelope rather than rewriting all memory. Measure missed obligations and false readiness first; context size and latency are secondary.
6. Switch only after reviewed source coverage, structural validation, source-to-task application replay, human confirmation, current-watermark readback, and a retained rollback source. Keep Graph v3 readable while building v4 and keep the active Guard on its accepted checker/snapshot while testing the candidate. Missing or unreadable records limit named routes; they do not trigger automatic invention, a global pause, duplicated tasks, or forced orchestrator rotation.

Name one integration owner for this migration. Collect participant deltas into the same candidate rather than concurrently replacing the shared graph. Resolve conflicting scope/chronology explicitly with the decision owner; a more recent local experiment does not silently override a shared accepted constraint. Include cross-domain retrieval cases contributed by participants, then ask each available orchestrator to read back the accepted watermark and retrieve the shared meaning relevant to its next work. This is bidirectional consolidation, not merely sending an update announcement. Record missing participants/sources and limit only affected coverage claims or unsafe work; do not claim whole-team coverage or stop independent work while waiting. A late delta is reconciled against the then-current watermark, not written over the accepted candidate.

Use Graph v4 with Project State v2 after cutover. Graph v3 remains readable migration evidence, so installing the framework does not invalidate an accepted project or claim that its memory was reorganized. Full v4 coverage requires the entity spine, Module Contracts, Source Coverage Ledger, cross-domain probe, source-to-task application replay, and accepted cutover above.
