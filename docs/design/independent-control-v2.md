# Independent Control Design Candidate

Date: 2026-10-06. Status: DESIGN, not installed behavior or a release.
Owner: framework maintainer. Objective: more retained accepted DOD progress per
whole-chain allowance and time, with fewer regressions and human recall prompts.
This document inventories existing responsibilities and proposes a control
arrangement; it grants no product mutation, deletion, model spend or new scheduler.

Read the [operating contract](framework-v2-operating-contract.md) for the unified
cycle and the [qualification and rollout](framework-v2-qualification-rollout.md)
for proof obligations, staged adoption and rollback. This inventory owns the
responsibility catalog; it is not an additional task prompt.

## One Manager, Separate Judgments

1. The orchestrator owns goal, prioritization, task contracts, assignments and
   parent acceptance. It receives decisions, gaps and evidence links, not search
   transcripts. An idea does not silently become the current DOD.
2. Preparation retrieves facts under an owned question. Reuse a current sufficient
   package; otherwise use the lowest proven capable profile. Preparation neither
   chooses the product goal nor invents a solution. Discovery resolves design
   uncertainty; Lab tests a bounded proposition, not a compulsory extra stage.
3. The executor owns scoped implementation, local diagnosis, tests, required
   documentation and artifact disposition. It reports an exact information gap,
   not a request to rediscover the entire project.
4. Independent REVIEW judges preparation readiness and, after the orchestrator's
   accept-work, the completed acceptance/retention cycle using the catalog below.
   It does not dispatch implementers, choose product priorities or operate tools
   on the product's behalf. Existing Guard detects delivery/liveness only.

These are independent responsibilities, not four mandatory persistent chats per
task. Reuse existing roles and evidence. A new fresh review context is bounded to
an episode and does not inherit the producer's persuasive discussion. Durable
findings, accepted dispositions and deadlines survive that context's end.

The post-accept trigger occurs after the orchestrator has accepted the product
result and performed or explicitly accounted for its memory/map/tracker/cleanup
work. It does not replace technical review before acceptance. The fresh checker
considers C01-C28, verifies applicable actual outcomes, and publishes only its
verdict through the existing result route. The host must ensure delivery and an
observable orchestrator disposition; an acknowledgement alone is not compliance.
The orchestrator remains accountable for knowledge integration and assigns any
repair. It cannot declare its own post-accept control closure. Missing checks or
delivery stay pending, with bounded reconciliation, rather than implicit success.
Subsequent review consumes original criteria and new evidence, not persuasive
conversation; unresolved history survives each fresh reviewer context.

The reviewer needs the accepted goal, public obligations and accessible primary
sources; a reviewer ignorant of the product cannot detect a semantically incomplete
brief. The orchestrator's selected packet is evidence, not the only allowed route.
The reviewer checks its selection against the module/goal index, source coverage,
public consumers and known open commitments. Missing routes remain explicit gaps.

Human changes remain authoritative within host permissions. Independence means
the reviewer cannot hide an observed violation to accommodate pressure. An actual
policy exception needs an authorized decision, affected scope, consequences and
return/expiry condition. Host permissions and security restrictions cannot be
waived by a framework receipt. Do not suppress direct human-worker communication;
reconcile material changes before conflicting subsequent work.

## Two Health Loops And Two Learning Streams

Do not collapse these into a single green health label or four permanent agents.
They reuse event evidence but have separate questions, ownership and outcomes.

| Concern | Accountable responsibility | Evidence and result |
| --- | --- | --- |
| Project health | Independent project Health Review; module/artifact owners repair | Retained DOD progress, module contracts, accepted versions, repo/branch custody, maps/docs/memory, data and security; produce scoped findings and verified repairs. |
| Orchestration health | Independent control REVIEW via external observation, not the manager under examination | Correct task entry, actual recall/application, permissions, leases, delivery/consumption, model/budget routing, observer coverage and continuation; restore the broken control route and prove it in the host. |
| Framework effectiveness learning | Framework maintainer accepts sanitized evidence from authorized project review | Source-backed episode of productive/unproductive work, alternative explanations, whole-chain cost and a bounded improvement hypothesis; validate before changing or publishing the framework. |
| Human collaboration learning | Separate bounded analysis of consented episodes; maintainer curates guidance | Useful interventions, unclear instructions, timing/recipient and scope changes relative to already-existing failures; produce evidence-qualified guidance, not a user score or blame. |

Healthy repository metadata does not prove useful DOD progress. Product success
does not prove reliable orchestration. An orchestration incident is not necessarily
a code defect. Numerous commits may be valuable history: inspect unowned residue,
unpublished success and regressions rather than optimize a raw commit count.

The orchestration-health route has the strongest independence requirement: its
enrollment, due state, source observations and findings cannot exist only in the
manager's selected packet/conversation. The manager cannot suppress its trigger,
edit the reviewer's verdict or close its own failure without repair evidence or
an explicit authorized exception. Actual protection depends on host permissions;
editable same-actor files do not become tamper-proof because they contain hashes.
Where independent scheduler/identity/read access is missing, mark LIMITED and
identify the human fallback rather than install a recursive watcher chain.

Learning is evidence reuse, not another per-tick audit or automatic self-modifying
framework. On a material completion/incident retain a compact episode: intended
outcome, model/framework version, applicable source revisions, action sequence,
observed result and retained success, failure classification, human corrections,
available usage/time, confounders and next falsifiable hypothesis. Minimize private
content; no secrets, whole transcripts or customer artifacts in upstream lessons.
Use existing task evidence and maintainer plan/evidence paths, not a new universal
database. Review recurring patterns and both successes/failures within a bounded
maintenance window; published rules change only after tests and release/adoption.

Recommendations remain evidence-qualified. A repeated outcome in one project is
not a causal law for all users, models or harnesses. Total control/research cost
belongs in the effectiveness measure; do not create learning work that consumes
the capacity needed to deliver the original outcome.

## Independent System Health Loop

Task acceptance and system health are distinct loops. Existing Health Review
owns system assessment through a fresh independent REVIEW episode. Maintenance
owners repair; the orchestrator schedules/integrates; REVIEW verifies repair.
This is not a second product manager, and no actor may erase its own unresolved
finding by declaring itself healthy.

Health admission must not depend on task dispatch/completion or the orchestrator
remembering to invoke it. Due obligations and observations survive outside its
conversation. A supported external host event/timer route collects inexpensive
metadata and evaluates due conditions; Guard remains delivery/liveness-only,
not a semantic judge. Reuse a supported scheduler/adapter, not another permanent
model-backed manager. Unchanged observations invoke no model where supported;
a model-backed fallback has explicit bounded cost, never a zero-cost claim.

This proposes stronger timing than active-session-only 1.x health rules; it does
not claim existing universal enforcement. Observation intervals and substantial
review windows are different. Retain the weekly allowance/reset budget policy
for deeper review, enroll due consideration independently of demo completion,
and do not replay all missed intervals or audit the entire system on every tick.

| Signal | Evidence and scoped response |
| --- | --- |
| Due observation/review without task completion | Check independent due state and source freshness; missing observation is UNKNOWN, not health. |
| Repeated human correction or same-class repair | Classify the actual repeated issue; check recall, preparation and retained baseline once, not every message. |
| Time/burn/no-progress exceeds the agreed task envelope | Compare to checkpoint and actual work; long duration alone does not prove failure. |
| Unexpected changed file/module/dependency surface | Compare responsibility boundaries to approved scope; require necessity evidence or bounded repair. |
| Unowned branches/worktrees, local-only results, old merged/rejected residue | Reconcile actual Git/PR/worktree inventory with owners and artifact dispositions, including objects absent from active-task lists; no deletion by count/age. |
| Excess parallel work or overdue cleanup | Compare to agreed capacity and retention conditions; preserve unique work before authorized consolidation. |
| Memory/map/docs drift or inaccessible operational route | Locate the source/meaning gap and owning repair, not global rediscovery or secret copying. |
| Context/usage growth or repeated identity/recall failure | Use actual supported metadata and recovery evidence; missing telemetry is unknown. Rotation needs a proven authorized handoff. |
| Missed controller result, expired exception, overdue repair | Reconcile the expected result and retained incident; do not indefinitely defer or self-certify recovery. |

Thresholds belong to accepted project policy and task envelopes, with provenance
and review conditions. Counts/age are investigation signals, not universal defect
verdicts. Keep severity, source version, first seen, last progress, owner, due time,
attempts and disposition in existing records. Deduplicate incidents and bound
review cost; renamed work or new messages do not reset failure history. Urgent
safety/authority failures hold only affected actions. Ordinary debt gets an owned
repair; independent productive work continues. Explanation alone is not closure.

Compare independent Git/tracker/runtime/authorized usage facts with self-reports.
Read-only observation, separation of producer/reviewer, source binding and durable
dispositions reduce accidental evasion, not make AI or the host impossible to
fool. Respect actual pauses and explicit goal changes. If no independent source
can detect the observer's own missed tick, disclose that common failure mode.

Adoption must prove: idle/absent manager, orphan artifacts, missed observation,
stale/self-serving report, legitimate long work, pause, duplicate signal, exhausted
budget, repaired finding with retained debt and quiet healthy ticks. Show actual
timed/event admission, independent verdict, owner repair and accepted readback.
These additional system-loop cases are NOT RUN; the earlier 39 tests do not prove
them. This design installs no scheduler or product behavior.

## Checklist Operation

The candidate [operational catalog](../../scripts/control-catalog.mjs) expands the
28 groups below into 87 explicit criteria with source routes and mechanically
required dispositions. It is not yet installed. The completeness checker does not
authenticate evidence or judge semantic applicability; see the
[assembly qualification](../evidence/framework-v2-assembly-2026-10-06.md).

The catalog is versioned with the framework, not memorized inside one system
prompt. At every new task, including a repeated task, select applicable items and
bind their dispositions to the actual task, source revisions, module version,
scope and policy version. Repeat work can reuse evidence only after those bindings
and unresolved obligations are checked. Ordinary unchanged turns do not rerun it.

Every applicable item must have an evidence-backed disposition: satisfied, repair
required, unknown, authorized deferral, or inapplicable with a specific reason.
These are conceptual states, not a new installed schema. Missing rows are not
implicitly satisfied. The producer cannot certify its own exceptional omission.
Relevance selection itself is reviewed: selectively hiding a responsibility is a
failure even when all supplied items are green. Absence of evidence is not failure
of the product but prevents claiming the corresponding guarantee.

Use deterministic checks for identities, completeness, revisions, due dates,
receipt pairing and actual metadata. Use semantic review for applicability,
meaning, source omissions, algorithm rationale and proof adequacy. A nonempty
field, a source hash or a schema-valid receipt cannot certify semantic coverage.
The catalog does not require a fresh paid judge for each already-proven item.

Keep one scoped result with findings, evidence, owner, next action and resolution
condition in the existing task/Return/Project State route. No parallel planner,
competing graph or second notification owner. A long applicable checklist can be
split into bounded sections with explicit coverage; delegate only a real specialist
question within authority, not one task per checkbox. Section results compose
without dropping cross-section obligations. The checker cannot become an infinite
review/repair loop: preserve attempt history and stop at the agreed decision gate.

Explicit policy differences to settle rather than silently pretend they exist:
- Published rules treat file length as a review signal, not a universal 600/1000
  line prohibition. Candidate project policy may prefer under 600 lines and
  require explained review above 1000; this is a PROPOSAL, not an installed cap.
  Generated/vendor files and cohesive code require explicit applicability handling.
- Shared planning and dates are required where relevant; fixed sprints are only
  used when the team agrees. The framework must not invent a sprint process for
  every project. Board reconciliation is required regardless of that choice.
- Rotation is not a daily quota. Frequent rotation can itself lose knowledge and
  cost more. Evaluate actual context/recall failures, preserve progress, and prove
  coverage at cutover; quiet operation does not independently certify health.

## Supported Enforcement And Its Limits

For 2.0 admission, implement only one supported host route first: prepared packet
-> applicable-check dispositions -> permitted execution -> exact-result review
-> orchestrator accept-work and retention/cleanup -> independent post-accept
control -> disposition and continuation. The manager cannot self-waive review of its
own omission. Mechanical checks bind evidence and independent disposition to the
current revisions; semantic review judges what those checks cannot infer.

Native tools outside that route remain a real bypass until the host intercepts
them. A prompt, JSON approval or signed-looking hash is not a sandbox or
authenticated authority. For unsupported hosts report advisory/LIMITED behavior,
not mandatory enforcement. Prove real installation and a fresh task at adoption;
never claim that unit tests or a scheduled observer alone establish this boundary.

Avoid new loops: preparation has no prerequisite preparer; the reviewer repairs
neither code nor its own evidence; genuine unresolved decisions return to the
existing owner. A failed item holds only dependent work. Keep a bounded repair
history, accept genuine repaired sources without reopening settled findings, and
retain remaining debt through missing or malformed replacement records.

## Cheap Qualification Plan

Begin with deterministic existing fixtures, not a new live project or model call.
Then use source-backed ordinary-language cases with an independent hidden rubric.
Sources and artifact access must be matched across baseline and candidate.
Expected obligations must be selected before seeing the model answer, and cannot
be chosen solely by the candidate's preparer. Do not label static coverage as
semantic retrieval or future reliability. Two kinds of errors matter: missed
obligations and needless stops/search/review.

| Scenario | Required behavior / failure to catch |
| --- | --- |
| Urgent repeat repair, no journal name in request | Recall applicable past purpose, successes, rejected methods and due ideas; distinguish exercised operators from an aspirational design before changing the algorithm. |
| Cost estimate after layout change, no hint about old pricing decision | Follow spatial entities through quantities, specification, pricing source/version/unit/region/currency/tax qualifications where source-backed and commercial artifact consumers; do not invent prices or read closed-module internals. Synthetic sources first; real cross-domain proof remains separate. |
| Design transfer during an active DOD | Recover design-system/accessibility/product intent and affected consumers; retain new optional ideas without expanding the task silently. |
| Manager sends a convincing but incomplete packet | Independently find an omitted applicable obligation through source routes; report coverage gap rather than rubber-stamp green local tests. |
| Same valid task continued, no material changes | Reuse matching proof and start the next authorized action; no repeated global Discovery or extra model judge. |
| Legitimate human change or explicit pause | Preserve prior evidence, record changed scope/exception and respect pause; independent review is not authority above the human. |
| Merged PR, squash history, dirty/foreign worktree, local-only commits | Preserve unique work and unknown ownership; clean only with exact evidence/authority, retain an owned exception otherwise. |
| Issue updated but board missing/stale | Distinguish task publication from actual board membership/status/link readback; do not announce synchronization. |
| Missing credentials route or unsafe pasted secret | Retrieve protected pointer and access scope, not secret bytes; missing access blocks that action, not the whole project. No real secrets in fixtures. |
| Lost Return, duplicate tick, unclear external outcome | Reconcile same result/owner; no duplicate action, no repeat expensive review or bypass of host denial. |
| Context loss, partial memory migration or rotation | Preserve open commitments and source meaning, recover by ordinary task query, prove cutover before retiring the old route. |
| Repaired source, remaining debt, large checklist | Accept the evidenced repair, keep other obligations and inspect every applicable section; no omitted-row PASS or endless restart. |

First do a source-path/catalog integrity check and existing deterministic stress,
instruction-routing and checkpoint-review tests. These establish only current
mechanics. The new complete control design and the pricing/repair retrieval cases
remain NOT RUN until a bounded inference pilot is separately scoped and authorized.
Previous grants are consumed, never carried forward by this document.

Executed on 2026-10-06: catalog integrity found 28 unique sequential items and
28 existing local source links. The existing `course-stress`, `instruction-routing`
and `checkpoint-review` suites passed 39 tests, zero failures/skips, zero model
calls. This is a baseline mechanical/structural regression check, not execution
of the proposed complete design or the new semantic scenarios. No new runtime
gate, independent model review, cost comparison or production adoption is proven.

Pilot go/no-go: no critical skipped obligation or unauthorized action; current
valid continuation does not gain an unjustified stop; retained behavior and
required new outcome are demonstrated; full cost and coordination included. State
unmeasured allowance and host coverage explicitly. Finite cases never prove all
future omissions impossible. Release 2.0 only for a proven changed operating
contract with migration/adoption, not a longer checklist or a version promise.

## Separate User-Interaction Study

Retain this as an optional research question, not a dependency of delivery or a
new monitor. Use a small consented existing sample with content minimization:
task difficulty/phase/model, existing debt, command time/recipient/type (idea,
correction, scope change, clarification), concurrent work, accepted progress,
rework, memory misses, time and attributable usage. No credentials or full private
transcripts belong in a public report.

Compare similar episodes; label confounding and unknowns. Human intervention often
follows an already failing task, so correlation cannot establish that the user
caused the failure. Do not optimize for fewer questions at the expense of informed
control. Candidate guidance: capture the desired outcome, distinguish an idea from
an urgent scope change, consolidate nonurgent feedback at checkpoints, and make
cross-thread decisions visible. Test benefit instead of blaming the user or
requiring them to remember the framework's rules.

### Draft Human Operating Guidance

This is proposed help content, not an empirically validated manual or new rule
the user must memorize. The orchestrator should infer and confirm intent in
ordinary language, asking only when ambiguity materially changes the action.

- State the desired observable outcome, preserved success and constraints.
  The system supplies source recall, preparation and its concrete next step.
- Ideas may be offered at any time. Distinguish a future idea from a requested
  priority change when possible; the system preserves the idea and recall trigger
  without silently expanding current work. Capture/ack is not proof of later recall.
- Product/priority decisions normally go to the orchestrator; precise local facts
  may go directly to an executor. A material boundary/goal change must return to
  shared control before conflicting action. Never punish direct communication.
- Interrupt immediately for wrong goal, unsafe action, data loss or unauthorized
  spend. Nonurgent suggestions can be collected for a checkpoint; silence is not
  a prerequisite for a functioning framework.
- When stalled, ask for the last proven result, exact blocker, remaining permitted
  step and owner. Do not require the person to create duplicate workers or repeat
  approvals; the system distinguishes a lost return from a genuine decision gap.
- When changing priority, explicitly preserve the current accepted result and
  choose what is deferred. The system records the consequence and revisit condition.
- Ask to see observable output and remaining limits, not only a PASS label.
  The user does not have to manually police maps, branch cleanup or model profiles.

Before shipping this guidance, evaluate matched existing episodes without exposing
private details. Separate advice supported by evidence from reasonable defaults
and untested hypotheses. Do not attribute all delay following a user message to
that message; record whether the task was already failing before intervention.
