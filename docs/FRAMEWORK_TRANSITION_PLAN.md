# Framework Efficiency Transition

Approved direction: 2026-09-29. Owner: framework maintainer. Status: IN_PROGRESS.
This is the durable plan for framework development, not a project instruction or an installed workflow. Read it when continuing this transition, not during ordinary product tasks.

## Outcome And Rationale

Increase retained accepted product outcomes per whole-chain allowance and time as architecture grows. Reduce repeated discovery, repairs of accepted behavior and human reminders. Shorter prompts, more rules, a new model or a version number do not establish that outcome.

The recurring failure is a combination of tangled implementation, unproven module autonomy, repeated context loading and conflicting control instructions. Do not assume modularization is already complete before testing its benefits. Test the transition from one useful legacy capability to a closed module, then its independent reuse. Do not require a whole-platform rewrite before the pilot.

Use one cycle: goal -> applicable decisions -> module boundaries -> sufficient context -> delivery -> proof -> retained result -> next action. Preserve human authority, explicit pauses, accepted releases, open obligations and shared meaning across models, harnesses and people.

Use sanitized cases: prepared lab input mistaken for complete success, consumer needing a private edit, a missing fact versus a missing design, interrupted Return, repeated signal, temporary maintenance delay and direct human control.
2. Inventory each old core obligation as retained invariant or routed event mechanic. Test trigger, owner, authorized action, stop/resume condition and retained result; matching prose is structural evidence only.
3. Run existing deterministic regressions and targeted negative tests. For access, include supported rejection and an explicit unsupported-route case, not just a conforming caller.
4. Agree a small model-evaluation budget before external runs. Keep inputs, baseline and acceptance fixed; change one instruction variant at a time. Stop for a demonstrated cause, not repeated broad reruns. Do not pause product work to isolate account limits without agreement.
5. In the project pilot, measure raw-input outcome, independent connection, retained behavior, elapsed/active time, input/cached/output tokens where observable, human corrections, retries and attributable allowance. Record UNKNOWN rather than deriving subscription savings from API prices.
6. Show transition investment separately from marginal reuse and expected payback. A small pilot establishes feasibility, not universal reliability or a guaranteed percentage saving. Rollout retains bounded observation and a return path.
